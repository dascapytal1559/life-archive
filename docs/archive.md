# The message archive

The friend map module's archive of messages, calls and hangouts, and the commands that read it.

## The message archive

The archive (friend map's, `data/modules/friend-map/archive.sqlite`, through Node's built-in SQLite with full-text search) keeps messages from each platform, one import person (account) per platform identity, and the person table (see people.md's "People"). It is filled by **connectors**, the friend map module's (`modules/friend-map/connectors/`, named in its `module.ts`, run by the core's host as the core's own are), one per source, each switched on or off in `data/connectors/<id>.json` (a missing file means off). There are twelve so far: Telegram and WhatsApp, live, through the bridge rig (see "Telegram, live" and "WhatsApp, live" below), and ten that import: two for Messenger (its phone export, and Facebook's "Download your information"), named by id since both serve Messenger, Instagram's "Download your information", WhatsApp's own databases, the Messages app's own database (iMessage and SMS), the phone's call history (calls, not messages), WeChat's own databases (from an iPhone backup), X's archive of your data, Signal Desktop's chat history export, and Discord's data package:

```sh
npm run archive -- enable messenger-export
npm run archive -- import messenger-export ~/life-archive-data/platform-exports/messenger/2026-09-27/   # the phone app's "Download your message storage data" zip, unpacked
npm run archive -- enable facebook-dyi
npm run archive -- import facebook-dyi ~/life-archive-data/platform-exports/messenger/2026-09-28/   # Facebook's "Download your information": its zip parts, unpacked
npm run archive -- enable instagram-dyi
npm run archive -- import instagram-dyi ~/life-archive-data/platform-exports/instagram/2026-10-05/   # Instagram's "Download your information", unpacked
npm run archive -- enable whatsapp-db
npm run archive -- import whatsapp-db ~/life-archive-data/platform-exports/whatsapp/2026-09-28/   # ChatStorage.sqlite and the rest, from an iPhone backup
npm run archive -- import whatsapp-db ~/life-archive-data/platform-exports/whatsapp/2026-09-28/ --contacts ~/life-archive-data/platform-exports/addressbook/2026-09-28/AddressBook.sqlitedb   # ...named from the iPhone's address book
npm run whatsapp-mac-calls                                          # the Mac WhatsApp app's calls alone, when they changed (every 15 minutes by launchd; see WhatsApp below)
npm run whatsapp-mac-calls -- install                               # writes and loads that launchd agent, local.whatsapp-calls-import; --dry-run prints it
npm run archive -- import whatsapp-db ~/life-archive-data/platform-exports/whatsapp/mac/ --settings '{"only": "calls", "callsFrom": "chats"}' --dry-run   # what an import would add, the archive only read
npm run archive -- enable imessage-db
npm run archive -- import imessage-db ~/life-archive-data/platform-exports/imessage/2026-09-28/ --contacts ~/life-archive-data/platform-exports/addressbook/2026-09-28/AddressBook.sqlitedb   # Library/SMS/sms.db and its attachments, from an iPhone backup
npm run archive -- enable call-history
npm run archive -- import call-history ~/life-archive-data/platform-exports/calls/2026-10-06/   # CallHistory.storedata, copied from the Mac's ~/Library/Application Support/CallHistoryDB/
npm run extract-wechat -- [<backup folder, or host:folder>]        # WeChat's files out of an iPhone backup (Finder's last, another here, or over ssh) into ~/life-archive-data/platform-exports/wechat/<backup date>/
npm run archive -- enable wechat-ios
npm run archive -- import wechat-ios ~/life-archive-data/platform-exports/wechat/2026-09-28/   # WeChat's iPhone databases and media, as extract-wechat took them
npm run archive -- enable x-archive
npm run archive -- import x-archive ~/life-archive-data/platform-exports/x/2026-10-01/           # X's "Download an archive of your data" (its zip, unpacked there when it holds media)
npm run archive -- enable signal-export
npm run archive -- import signal-export ~/life-archive-data/platform-exports/signal/2026-10-02/   # Signal Desktop's "Export chat history" (or the folder holding it)
npm run archive -- enable discord-package
npm run archive -- import discord-package ~/life-archive-data/platform-exports/discord/2026-10-05/   # Discord's data package (its zip, or the folder holding it)
npm run archive -- coverage                                        # what is covered, and how stale it is
npm run archive -- import-status                                   # each connector used, how far it reaches, and what to do next
```

**Import sessions.** To bring every platform up to date at once, follow `docs/import-runbook.md`: for each connector, where a fresh copy comes from (live through the bridge rig, an app's database on this Mac, an iPhone backup, or the platform's own export), how long it takes, where it goes, the commands, how to check it, and the steps a computer-use agent can take, marked where only the captain can go on. A session starts with `npm run archive -- import-status` (`modules/friend-map/server/importStatus.ts`), which reads the archive for the connectors with an import that finished well (the platforms in use), groups them by that way, and gives each one's last import, how far its imports reach (the latest end of what they claim to cover), or, for a live one, its state and its platform's newest message, and the next step, with the day to ask an export to start from where the platform lets you choose; a platform whose live connector is connected needs its imports only for a gap. Then it lists the connectors never imported, each with how to start. Each connector's manifest says how a fresh copy is had (`obtain`, in `server/connectors/contract.ts`), and a test holds every one to having it, and a section of the runbook under the right way.

**Messenger's phone export** (`messenger-export`). Importing the same export again changes nothing, and a newer export of an overlapping period adds only what is new, so re-export from the Messenger phone app every few weeks and import it. Messenger's export has no message ids and only display names: messages get ids made from their content (photos sent together, a record each in one millisecond, by their place among them, since each export names their files anew), accounts are keyed by name, and each "Facebook user" chat (a deleted or unknown account) is a separate person that is never proposed for a merge. A chat is kept by its people, and a group or a "Facebook user" chat by its name too: the export names each chat's file `<name>_<n>.json` and writes the same `<name>_<n>` in it, `<n>` the chat's place in that export, which moves from one export to the next, so that number is taken off (only it: a chat whose name ends in digits keeps them), and a "Facebook user" chat with no messages is told from another only by its order. Until 2026-10-15 the number was kept, and a "Facebook user" chat with no messages was kept by the export's newest message, so a newer export brought every group and "Facebook user" chat in again, as a copy with a deleted-account person of its own; and photos sent together were told apart by their file names, so a newer export brought them in again in any chat (and their twins in a group's copy could not be found). `npm run archive -- repair messenger-phone-chats` finds those chats by their ids (each must be the one the old way gives its people and title, and each message's original record must give its id: photos sent together whose ids were made from their file names take their places among them as the import that brought them had them; an unsent message's record keeps no text, though its id was made with the text the export gave it, so that text is looked for in the phone exports under `data/platform-exports/messenger/` and taken only when it gives the id back; nothing is kept of it), says which it would merge (its dry run), and with `--apply`, after a checked backup (refused without one), gives each first chat and its messages their new keys (a one-to-one chat with a named person keeps its key, and only its photos sent together take new ids), merges every copy into it, and every message a chat holds twice, into the first (a message both have is kept once, with the newest export's attachments; who was taken out of a copy or unlinked from it stays so; a copy's drop is not carried, the first chat's own is kept), deletes the copies and their deleted-account people, and runs the rules. Run again, it finds nothing to do. Until it has run, a `messenger-export` import (and its dry run) is refused while any phone-export chat is still under its old key, or (the import alone: its dry run's copy has no records to tell by) holds photos with ids made from their file names, since it would bring them in once more. It keeps a call as an empty link (no text, no media, nothing about how long it was or whether it was answered), so such an item is read as a call of no known length.

**Facebook's "Download your information"** (`facebook-dyi`), with Messages chosen and JSON as the format, reaches back to your first message: chats that moved to end-to-end encryption (their history before the move), archived, filtered and message-request chats, groups and pages. A big download comes as several zips; put them together in one export folder, `data/platform-exports/messenger/<export date>/`, unpack them there (`exports unpack`, which unpacks a zip stored inside a part too, and a file repeated in several parts once), and import the folder as one export, a chat at a time; each attachment points at its file there and nothing is copied (see data.md's "Platform exports"). A later download, even of only the weeks since, goes in a folder of its own and continues the first. Facebook escapes every string (UTF-8 bytes written as Latin-1 characters) and the connector decodes them. Like the phone export it has names only, so accounts are keyed by the same names (a person is one account whichever export named them), and each "Facebook user" chat is again its own person. A chat is keyed by its thread id (the number ending its folder name), and a message by its chat, sender and millisecond, so a later download finds the same ids, and an edit or unsend updates the message already there. The phone app's export holds only end-to-end-encrypted chats and this one the rest, so the two mostly complement each other; the connector works out who you are as the name in most chats (set `"selfName"` in `data/connectors/facebook-dyi.json` if it can't). A big download (many parts, tens of GB, most of it media) takes a few minutes; progress is shown as it goes. If an import is interrupted, the archive is left as it was, and running the same command again redoes it without duplicates.

**Instagram's "Download your information"** (`instagram-dyi`, platform `instagram`), requested in Accounts Center with Messages chosen, all time and JSON as the format, comes as one zip in Facebook's format, so the two connectors share one reader (`modules/friend-map/connectors/metaDyi.ts`, with `metaDyiParts.ts` for the files): the same participants and messages, the same escaped strings, accounts keyed by display name (Instagram gives the username for someone with no full name, which counts as a name), chats by thread id and messages by chat, sender and millisecond, so a later download finds the same ids. It reads the inbox and message requests; a request you never answered is a chat only they wrote in, which the archive rules archive, and one you answered is a chat like any other. `reported_conversations.json` is not read. A chat with an invite link is a group, even with two people left in it (in Facebook's download too). Its photos, videos and voice notes are kept where they are, as every export's are: put the zip in `data/platform-exports/instagram/<export date>/`, unpack it there (`exports unpack`), and import that folder; each attachment points at its file there and nothing is copied (the zip itself is refused, and so is a folder anywhere but under `data/platform-exports/`). Instagram has no Marketplace. "Instagram User" (a deleted account) is a different person in each chat, as "Facebook user" is. The captain is found as the name in most chats (or `"selfName"` in `data/connectors/instagram-dyi.json`).

**The same message from both.** The two exports give a message different ids, so the archive matches them: a message whose id it has not seen is compared with those *another* connector brought in, and one with the same sender account and the same millisecond is the same message. It is kept once, and the new id is recorded as an alias of it (`message_alias`), so importing either export again, in either order, adds nothing; reactions from both add to it once, and its attachments stay those of the export imported first. Two "Facebook user" senders count as the same sender here, since each connector keys unknown accounts its own way; each connector's "Facebook user" is still its own person, never proposed for a merge. Messages from the same connector are never matched this way, since its own ids already tell its records apart. One difference remains by design: the phone export writes a burst of photos as one record per photo and the download as one message with them all, so that burst counts as the records of whichever export was imported first.

**WhatsApp.** `whatsapp-db` reads the databases the WhatsApp app keeps, from a folder holding `ChatStorage.sqlite` (required), `CallHistory.sqlite` (the Calls tab, for calls; see below), `LID.sqlite` (phone numbers behind LIDs), `ContactsV2.sqlite` (WhatsApp's copy of the address book, which an iPhone backup does not have) and `Message/Media/` (the media files); the iPhone app and the Mac app keep the same files with the same ids, so a folder taken out of a local iPhone backup and, later, a copy of the Mac app's folder both work, each copied into its own `data/platform-exports/whatsapp/<date>/`, where its media then stay. For names it also reads the captain's address book: the iPhone's `AddressBook.sqlitedb` beside `ChatStorage.sqlite`, or the one named with `--contacts` (for that import) or `"contacts"` in `data/connectors/whatsapp-db.json`, which may also be a copy of the Mac's Contacts (a folder, `platform-exports/addressbook/<day>/`; see data.md's "This Mac's calls and Messages, every 15 minutes"); given with `--contacts`, the import also fills people's notes from it (see people.md's "Notes" under People). It copies every database to a temporary folder in the archive's `platform-exports/` (the copies hold every chat) and reads it there, never writing to the source.

**A dry run.** Any import can be tried first with `--dry-run`: the connector reads its source as for the import, and its records are applied to a copy, in memory, of what the archive keeps of that platform (without any message's text), so it prints the counts the import would make, and each call it would add (when, which way, how long, with whom), while the archive is only read: never opened for writing, its rules never run (`server/archive/dryRun.ts`). It counts every reaction as new, since the copy leaves them out. `--settings '<json>'` gives any import settings of its own, over the connector's, as `--contacts` gives one. Everything is keyed on WhatsApp's own ids, so importing the same folder again changes nothing and an overlapping copy adds only what is new:
- An account is its phone JID (`61491571266@s.whatsapp.net`, with the number as its handle) whenever its number is known, directly or through its LID (WhatsApp's newer account id, resolved through `LID.sqlite`, the chat list, or `ContactsV2.sqlite`), and its LID (`…@lid`) otherwise. Its name is the first of: your address book's name for its number (the address book given, then `ContactsV2.sqlite`; when several cards have the number, an iPhone's book names it from its first card, the Mac's Contacts from the card changed last), its one-to-one chat's name in WhatsApp, the push name the person gave WhatsApp, its name in a group's member list, its phone number, and "WhatsApp user" (never proposed for a merge); a name that is only a number is passed over, however it is typeset (WhatsApp writes numbers wrapped in direction marks, grouped with no-break spaces and with a non-breaking hyphen), and so is a base64 protobuf message, which the iPhone app keeps in the columns for a message's push name and a group member's first name ("COC7/7cGIAA=", "+EAA="; `isEncodedName` in `server/archive/names.ts`). An address book name is the contact's first, middle and last names, leaving out a part the name already ends with, so a full name typed as the first name ("Ada Sample", last name "Sample") is not doubled. An address book number typed with its country code (`+61…`, `0061…`) must match exactly; one without (`0491 571 266`) matches a WhatsApp number that is a one-to-three-digit country code followed by it. The import prints how many accounts each source named. Your own account is `me`, named "Me" or `selfName` in `data/connectors/whatsapp-db.json`; any number on your own address book card is you, as is a group member row one of your own messages names, and `selfJids` (a list of JIDs, LIDs or numbers) names any other. Without an address book, set `selfJids`, since a backup's group messages from you name no member row.
- A chat is its JID: the other person's account, or the group's `@g.us` JID (a community's announcements group is a group too). Status updates and broadcast lists are skipped (the copies of a broadcast message in each recipient's chat are kept).
- A message is its stanza id (`ZSTANZAID`), with its chat added when the same id is in several chats, or a hash of its chat, time, type and sender when it has none. Deleted messages are kept as unsent, without text. System messages ("security code changed", "you created the group") have no sender and never count as talking with anyone. Image, video and GIF captions become the message text. Reactions, quoted replies and edits are not read yet.
- **Calls.** WhatsApp keeps each call twice over: in `CallHistory.sqlite`, the Calls tab (when it started, how long it was connected, its outcome, which way it went, voice or video, and who else was on it), and, since late 2023, as a call record in the chat it was made in (a message of WhatsApp's type 59, whose media item keeps WhatsApp's own record of the call). Each call becomes one call record, as the other apps' are (see "Calls" below, and "How closeness is scored"), keyed by WhatsApp's call id, so the two copies of a call, the same call in a newer backup or the Mac app's folder, and an old import's record are one: the chat's own when it has one, else one made from the Calls tab in the chat it was made in (the person's one-to-one chat, made for the call when there is none, or the group's), at the time it started (the Calls tab dates an outgoing call about when it ended, so it starts at that date less its length, late only by the ringing). One made from the Calls tab only stands in for the chat's own (`fallback` on its event): it adds the call when the archive lacks it, and otherwise only gives a call of no known length its length, since the Calls tab can say a second more than the chat's record. A call is one call whichever table keeps it: a call record and a call in no chat with the same id are the same call, so a copy that names several people on a call another copy kept in a chat, or the other way round, adds nothing, and can only give the call a length it had none of (`write.ts`). It is as long as it was connected, 0 when nobody answered, and of no known length when you answered it on another of your devices (only that device knows how long; give it one with Add length). The oldest calls have no call id, and get one made from their time and who was on them. A call the Calls tab keeps with several people and no group (a three-way call started outside a group chat) is a **call in no chat**, as the phone's calls are (the `call` table, one row for each person on it, by its call id): with everyone on it whom the copy has a chat with (one-to-one or group), the rest counted as its unnamed others ("+1 other"), which way it went, voice or video, whether it was answered and how long. It is a call with each of them: in each one's chat ("Call · 12 min", "WhatsApp · with 2 others") and the Calendar (one row, "Ada and Bruno +1 other · on WhatsApp, they called"), and in the closeness score each takes their share of its time among everyone on it, as on a call you logged with several people (`groupSharedPart`). Importing a newer copy brings its time, length and outcome up to date; who was on it stays as the first copy said, since a copy's list can be wrong (the Mac app's often is). One answered on another of your devices has no known length and counts nothing (Add length is only for a call in a chat). One with no one at all, or with no one the copy has a chat with, is left out and counted. WhatsApp's per-person outcomes in the Calls tab do not agree with the call's own, even on one-to-one calls, so everyone it lists counts as on the call. The iPhone's Calls tab holds only the calls the app still lists, so import each backup's. The live bridge passes on no call (see "WhatsApp, live"), so a call reaches the archive the next morning from the Mac app (below), or with the next backup. A message an older import kept as of another kind (as these call records were, before calls were read) takes its kind, and its sender, from the next import that can tell it; a kind once known is never taken away (`write.ts`).
- **The Mac app's calls, every 15 minutes.** The Mac app keeps the calls too, the phone's included (it syncs them while it is linked), so `npm run whatsapp-mac-calls` brings them (`modules/friend-map/connectors/whatsapp-db/macCalls.ts`; the agent installed before the module runs the old path, `server/connectors/whatsapp-db/macCalls.ts`, which hands on to it until it is reinstalled), run every 15 minutes and at load by the launchd agent `local.whatsapp-calls-import` (logging to `/tmp/whatsapp-calls-import.log`), its only schedule, since whatever this Mac can already read syncs every 15 minutes, in one slot (see data.md's "This Mac's calls and Messages, every 15 minutes"). `npm run whatsapp-mac-calls -- install` writes and loads the agent, from the checkout whose archive takes the calls. One run at a time (`whatsapp-mac-calls/lock` in the archive's folder). After the copy below, it reads the merged copy's calls' fingerprint: how many call records the chats keep and the newest's id, and how many calls the Calls tab keeps, the newest's id and their seconds connected in all (so a length that came later counts), nothing of who or when. When that is as at the last import that went well (`whatsapp-mac-calls/state.json`), the run keeps no copy, imports nothing and logs one line; else it keeps the copy and imports, as follows. It copies the app's four databases (`ChatStorage`, `CallHistory`, `LID` and `ContactsV2`, each with its `-wal` and `-shm`) out of `~/Library/Group Containers/group.net.whatsapp.WhatsApp.shared/` twice with `cp -p`, never opening them there, and keeps the copy only when both are the same byte for byte (else the app was writing: it tries again ten seconds later, three times in all); merges each with its `-wal` into one file with SQLite's backup, from the copy opened read-only (never `immutable=1`, which would pass over the `-wal`), into `platform-exports/whatsapp/mac/` in the archive's folder, which each run whose calls changed replaces; and imports that folder's calls alone. Its Calls tab cannot be trusted as to who was on a call: it lists one participant on nearly every call, and for about half of them not the person the call was with. So the import's settings are `only: "calls"` (calls alone: the call records, the chats they are in and the people on them, each only added if the archive lacks it, its names and titles left as the bridge and the fuller imports gave them; no message text is read, no coverage claimed), `callsFrom: "chats"` (the chats' own call records, and a call only the Calls tab has only where the copy bears out who it was with, in a chat the copy has: an incoming one with whoever called, an outgoing one with its one participant only when that person's chat holds a call record within the hour; never a call in no chat; the rest are counted and left out, old calls the iPhone's copy has), and `bridgeDb`, the bridge's database, whose LID map gives the number behind a LID the copy has none for (the Mac's `LID.sqlite` has none), read-only. So it adds only the calls the archive lacks, and a second run adds nothing. `npm run whatsapp-mac-calls -- --dry-run` makes the copy and says what the import would add. It needs the Mac app linked and running (the phone online every 14 days, as for the bridge), and macOS may ask, once, to let the job read the app's folder **[captain]**. Do not import the Mac app's folder without these settings: its Calls tab would put calls with the wrong people.
- WhatsApp people appear in People like everyone else, joined with anyone of exactly the same name, and proposed as the same person as another by the usual rules (one name contained in the other, or the same phone number as another account); see people.md's "People" below.

**iMessage and SMS.** `imessage-db` reads the Messages app's own database, which holds iMessage, SMS and RCS alike (all one platform, `imessage`): the iPhone's `Library/SMS/sms.db` with its `Library/SMS/Attachments/` folder, as taken out of a local iPhone backup (name the folder holding `Library/`), or the Mac's `~/Library/Messages/chat.db` with its `Attachments/` (copy that folder into `data/platform-exports/imessage/<date>/` and name it, or the file there), since attachments are kept where they are, under `data/platform-exports/`. Both keep one schema and the same ids, so the Mac's copy adds only what the phone's did not have; `npm run mac-imports` copies and imports the Mac's every 15 minutes when it has something new (see data.md's "This Mac's calls and Messages, every 15 minutes"). Names come from the address book, as for WhatsApp: an iPhone's `AddressBook.sqlitedb` in the folder named, or the one given with `--contacts` or `"contacts"` in `data/connectors/imessage-db.json` (a copy of the Mac's Contacts, as mac-imports passes it, or an iPhone's); given with `--contacts`, the import also fills people's notes from it. The database is copied to a temporary folder and read there, never written to.
- An account is its handle: a phone number in E.164 (`+61491571266`, its handle too), an email in lowercase (likewise), or the name or short code a business texts from. Its name is your address book's name for the number or email (unless that name is only a number), or else the handle itself. Numbers are matched to the address book as for WhatsApp. Your own account is `me`, named "Me" or `selfName`; any number or email on your own address book card is you, as is any handle in `selfHandles` (a list of numbers and emails).
- A one-to-one chat is the other person's account, so their iMessage and SMS chats are one conversation; a group is its `chat_identifier` (`chat…`), titled by the name the group was given. A chat is a group when the Messages app marks it so, even if everyone else has left, or when more than one other person is in it.
- A message is its `guid`. Its text is the `text` column, or else the string inside `attributedBody` (where newer iOS keeps it), less the characters that mark where attachments sit. Group events (someone added or left, a new name) are system messages with no sender. An edited message keeps its latest text and when it was edited; one taken back is kept as unsent, without text. A reply points at the message it answers.
- Tapbacks (heart, thumbs up, "Ha ha" and the rest, and any emoji) are reactions on the message they point at, not messages; one taken back later is left out.
- Link previews' data files (`.pluginPayloadAttachment`) are not attachments: the message is a link. The import counts messages by service (iMessage, SMS, RCS).

**Calls.** `call-history` reads the phone's call history (platform `phone`): `CallHistory.storedata`, the database the iPhone keeps its Recents in, which iCloud syncs to the Mac at `~/Library/Application Support/CallHistoryDB/` (an unencrypted iPhone backup leaves it out). Copy it (with SQLite's `.backup`, or while nothing writes it) into `data/platform-exports/calls/<date>/` and import that folder, or the file; it is read from a temporary copy, never written. Calls are not messages: each is a row of its own (`call`), with when it started, how long it was connected, which way it went, whether it was answered, and over what (`phone`, `facetime-audio` or `facetime-video`), keyed on the call history's own id for it, so importing a newer copy adds only the calls since (and brings up to date one whose record changed). They count in no message count, last spoke, trend or archive rule; they show in the person's panel and count toward closeness (see "How closeness is scored"). An incoming call is answered when the phone says it was picked up; an outgoing call never says, so it is answered when it was connected at all, which a voicemail is too. Calls through other apps (WhatsApp, say: their calls are in their own data, read by their own connectors), group FaceTime calls and calls from a withheld number are left out and counted.
- The other party is an account keyed as `imessage-db` keys one: a number in E.164 (the phone's own normalised form of it, else the number as written, read as `normalizeHandle` reads any handle, so `0491 571 266` is `+61491571266`), an Apple ID in lowercase, or a short code as written. It is named by the name the call history kept for it, if any, else your address book's (in the folder, or `--contacts` or `"contacts"` in `data/connectors/call-history.json`, as for iMessage; it fills no notes), else shown by its number.
- **A number someone holds in iMessage is theirs.** The rules put each call account on the person who holds exactly that number or Apple ID as an iMessage account (`linkCallsToNumbers` in `modules/friend-map/server/people.ts`, link `rule:same-number`): the same phone line, so there is no proposal to confirm. Importing the calls before the messages works too: the person the import made for a number goes once the number turns up in iMessage. A call account the rules linked follows that iMessage account wherever it goes ("Not them" on it, say, takes its calls along); one you placed yourself ("Not them" on the call account, `person link`) stays where you put it. A number nobody holds in iMessage becomes a person of its own and follows the other rules: joined by exactly the same name, proposed on the same phone number as a WhatsApp or Signal account, and archived with no messages until you name or keep them.
- `npm run archive -- calls` lists everyone you have called or who called you, the most time on answered calls first (how many were answered, for how long in all, how many were not, and the last); `calls <person>` lists one person's calls. Both count Messenger's, Instagram's, WhatsApp's and Telegram's calls in one-to-one chats too (theirs say how long they were), WhatsApp's three-way calls (one person's list says which app and how many others were on each), and any call you gave a length. SQL sees them all, WeChat's and Signal's as well, in the view `person_call` (see queries.md's "SQL queries").

**WeChat.** `wechat-ios` reads WeChat's own databases as the iPhone app keeps them (platform `wechat`), which an unencrypted iPhone backup holds as plain SQLite; nothing touches WeChat's servers or the app, and the Mac app's databases, which are encrypted, are not read. `npm run extract-wechat` takes them out of the backup: with no folder, the one Finder took last (the newest in `~/Library/Application Support/MobileSync/Backup/` holding a `Manifest.db`, which Finder brings up to date over Wi-Fi; docs/import-runbook.md, "Taking the backup"), refusing one whose `Status.plist` says it has not finished; or name the backup's folder on this Mac, or `host:folder` for one kept on another machine and reached by ssh (the backup is only read; its `Manifest.db` is copied here to a temporary folder to find WeChat's files, `modules/friend-map/connectors/iphoneBackup.ts`). It copies, for each account, `DB/WCDB_Contact.sqlite`, `MM.sqlite` and `message_<n>.sqlite` and the chats' `Img`, `Video`, `Audio` and `OpenData` folders, at the app's own paths, into `data/platform-exports/wechat/<the day the backup was taken>/`, filled under a temporary name and never written over (`--date` names another day), and prints counts only; run it again on a newer backup and import that folder too. The connector reads a copy of each database. Everything is keyed on WeChat's own ids, so importing the same folder again, or a newer backup's, adds only what is new: an account is its wxid (`userName`: `wxid_…`, an older id its owner chose, or a group's `…@chatroom`), named by your remark for them, else their WeChat nickname, else shown by the id (a group member who is not your contact, whom the archive rules archive as no name), with the WeChat ID they chose as its handle; a one-to-one chat is the other person's id, a group its `@chatroom` id with its member list and anyone who wrote in it; a message is its `MesSvrID`, its chat added when the same id is in two chats, or a hash when it has none. You are `me` (named "Me" or `selfName` in `data/connectors/wechat-ios.json`): the account's folder is named by the md5 of your wxid, so you are the id among the contacts and group members whose md5 it is (or `selfWxid`). Who sent a message: you when WeChat marks it sent (`Des` 0), the other person in a one-to-one chat, and in a group the id its content starts with (`<wxid>:\n`); notices and system messages have no sender. A photo is its full or HD copy, or the thumbnail when that is all the phone kept (a photo never opened); videos, voice notes (silk `.aud`, offered as a download) and files are kept in place; stickers are not in the backup. Links keep their address and a reply its words and what it answers. WeChat has no reactions or edits. WeChat compresses some messages (every photo, voice note, video, sticker and app message, and long texts) with a zstd dictionary that lives in the app, not the backup (numbered in the message, dictionary 5 in the backup this was built on): without it, such a message is kept without its content when its sender is known anyway (yours, and every message in a one-to-one chat), and a group message from someone else is skipped, since its sender is inside; the import counts both. Given the dictionary (`"dictionary": "<file>"` in `data/connectors/wechat-ios.json`), it reads them all, and importing again then fills in what was missing. WeChat's own chats (File Transfer, its notices) and official accounts (`gh_…`) are skipped and counted.

**X.** `x-archive` reads the direct messages in X's "Download an archive of your data" (platform `x`): the zip X sends, read in place and never extracted, the folder it unzips to, or a folder holding just the zip. It reads one-to-one chats (`data/direct-messages.js`) and group chats (`data/direct-messages-group.js`), each file the script X writes (`window.YTD.<name>.part0 = [...]`, a big archive adding `-part1.js` and on; anything else is refused, naming the file), with their media from `data/direct_messages_media/` and `data/direct_messages_group_media/` (the t.co link X writes into a message for its photo is taken out of the text). Everything is keyed on X's own ids: an account is its numeric user id, a chat its conversation id, a message its id, so importing the same archive again, or a newer one that overlaps it, adds nothing twice. You are the account in `data/account.js`. The archive names no one else in a chat, only their id: a person is named from your own tweets that mention them (their display name and @handle), else by the @handle a tweet of yours replied to (a name, as any username is), else by their id, which the archive rules archive as no name until you name them. Tweets, likes, followers and following are never messages or people (the follower and following lists hold only ids). Group joins, leaves and renames say who is in a group and what it is called, and are not kept as messages; a group of any size is read, and the archive rules decide who in it stays on the map. Reactions are X's seven (❤️ 😂 😲 😢 🔥 👍 👎). X's newer end-to-end-encrypted chats (XChat, in `data/message-event.js`) cannot be read from the archive; the import only counts them. The archive holds no calls: its direct messages are messages, joins, leaves and renames, and XChat's events are messages, read marks and key changes.

**Signal.** `signal-export` reads Signal Desktop's "Export chat history" (Settings > Chats; platform `signal`): the folder it writes (`signal-export-<date>/`, holding `metadata.json`, `main.jsonl` and, when media were included, `files/`), its `main.jsonl`, or a folder holding just that folder. `main.jsonl` is Signal's backup format (`Backups.proto`) written as JSON, one frame a line after a header line; anything else is refused, naming the line, never quoting it. To get one, relink Signal Desktop with "Transfer message history" so it holds what the phone does, then export; Desktop leaves disappearing messages out. Everything is keyed on Signal's own ids, never the export's own numbers: an account is its ACI (a UUID), else its PNI (`PNI:<uuid>`), else its phone number; a one-to-one chat is the other person's account, Note to Self is `me`; a group is `group:` and the start of a SHA-256 of its master key (the key itself, which would let anyone into the group, is never kept); a message is its chat, its sender and its first sent time, as Signal itself names one, so importing the same export again, or a newer one that overlaps it, adds nothing twice, and an edit updates the message already there. A contact is named as Signal names them: your nickname for them, else your address book's name, else their profile name, else their username, else their phone number, which in E.164 is their handle too, so the name and phone rules (see people.md's "People") join or propose them with whoever you know elsewhere. You are `me`: the export never gives your own id, but every group lists you with everyone else, and everyone else has a contact of their own, so the group member without one is you. A group's people are its members and invited members as Signal last saw them; someone who left and never wrote is missing. Edits keep the latest text and when it was edited, deleted messages are kept as unsent without text, a quote is a reply to the message it names, reactions are any emoji, one-to-one calls are calls (with no length, as Signal does not say how long a call was, but 0 long when Signal says it was missed or not answered), and stickers are stickers. Group changes, safety-number and profile changes, timers and group calls are only counted, as are one-to-one chats with no messages and contacts in no chat, which are not imported (Signal lists a chat for every contact it knows). Attachments are found in `files/` by the name Signal gives each (a SHA-256 of its plaintext hash and local key); an export made without media has none, so each is recorded as missing.

**Discord.** `discord-package` reads Discord's data package (Settings > Data & Privacy > Request your data; platform `discord`): the zip Discord emails a link to (`package.zip`), read in place and never extracted, the folder it unzips to, or a folder holding just the zip. Only the Messages section is needed: `Messages/index.json` gives Discord's label for each channel ("Direct Message with <username>", "<channel>, <server>", a group DM's name), and each `Messages/c<channel id>/` holds its `channel.json` (its type, and a DM's or group DM's recipients by user id) and `messages.json`; anything else is refused, naming the file, never quoting it (an older package's `messages.csv` is not read). The package holds only your own messages, never anyone else's, so every chat from it is marked as holding only your side (`conversation.is_self_only`), and the archive rules never read the others' silence there as a one-sided chat (see "Who is archived"). Everything is keyed on Discord's own ids: an account is its user id, a chat its channel id, a message its id, whose top bits give when it was sent to the millisecond, so importing the same package again, or a newer one that overlaps it, adds nothing twice. You are the one recipient in every DM and group DM (or the `selfId` setting in `data/connectors/discord-package.json`, which the import asks for when that cannot tell). A one-to-one DM is you and its other recipient, a group DM its recipients, and a server channel only you, since the package names no one else in it, titled as Discord labels it. A person is named by your nickname for them, else their global name, both only when the package has the Account section (`Account/user.json`, your friends); else by their username, from Discord's label for your DM with them, which is also their handle and counts as a name, as an X or Signal username does; else by their id, which the archive rules archive as no name until you name them. Discord writes "Deleted User" in place of a deleted account's id (and labels a DM with one "Unknown Participant"): that is one account keyed by the name, as Messenger's "Facebook user" is, and the archive rules archive it as a deleted account. Attachments are links to Discord's servers, so each is recorded as missing, unless a file of its name sits in its channel's folder. A message with neither text nor an attachment (a call, a sticker, an embed) is kept, without text, and counted: the package gives a message only its id, time, text and attachments, never its kind, so Discord's calls cannot be read from it. Reactions, edits, replies, and messages you deleted are not in the package.

For every connector, photos, videos, voice notes and other files are kept where they are in the export under `data/platform-exports/`, which must be unpacked there, or, from a live bridge, copied into the platform's `live/` folder there by content hash (see data.md's "Platform exports"); any the source lacks are recorded as missing. Each import prints what it skipped and why, by count. Dates and "last spoke" count days in local time.

**Who is archived.** An archived person is off the map and every view until you untick **archive** in the Query bar's Hide (one archive: those you archived and those the rules archived alike, see friend-map's "The Query bar"; their panel says which, and the rule's reason), joined with anyone of exactly the same name of two words or more or in Chinese, and proposed as the same person as another only on the same phone number (neither when you archived them yourself), and still listed in People under "Archived", with the reason, and found by search; all their messages are kept. Your choice always wins, and is kept in their tags: the tag `archive` archives someone whatever else is true, and `keep` stops the rules below archiving them. Anyone you have edited (named, given an alias or tag, merged, or added by hand) is kept too. Everyone else is archived by the first rule that fits, worked out from their messages on every platform when the rules run (after every import, and when you merge or split them) and stored with them:

- a deleted or unknown account ("Facebook user", "Instagram User", "WhatsApp user", "Telegram user", Discord's "Deleted User", or no name at all);
- no name: every account is known only by a phone number, an email, the SMS short code or sender id it texts from ("78787", "CommBank"), or the platform's own id for it (an X, Signal, Discord or WeChat user id), because no name came from the address book, a chat title, a WhatsApp push name, a Facebook profile or a username (`isUnnamed` in `modules/friend-map/server/archiving.ts`: an `id`-keyed account shown by its own key, or any name shaped like a number or an email, ignoring direction marks and reading any space or dash as a separator, or data WhatsApp kept as a name, such as "COC7/7cGIAA="; a username or handle someone chose on an internet chat platform, such as Discord's, Telegram's, X's "@ada_sample" or Signal's, is a name, since it is never the account's key there, the user id is, and it is shaped like neither a number nor an email);
- only Marketplace chats;
- direct chats where only they wrote (message requests, filtered chats);
- direct chats where only you wrote, from a source that would hold their side: a direct chat from Discord's data package, which holds only yours, counts as two-way once you wrote there, since their silence in it is not known (`you_direct_self_only` in `modules/friend-map/server/stats.ts`);
- they wrote only in group chats;
- they are in group chats and never wrote;
- no messages at all.

The two group rules pass over anyone in a **small group chat you wrote in**: twelve people or fewer, you included, on any platform (the same line the live bridges read by, below), where you sent at least one message. They are kept whether or not they wrote there, so friends met in small groups show up while big, noisy groups stay archived; a small group you never wrote in (a spam group you were added to, say) keeps no one, and its people fall to the group rules as in any group; the rules above the group ones (unknown, no name, Marketplace, one-sided direct chats) and your `archive` tag still win. A group's people are its members as the import listed them, plus anyone who wrote in it. Every connector lists members (iMessage the chat's handles, WhatsApp its group member rows, Telegram the room's joined and invited members, X everyone its archive's joins and leaves name, Signal the group's members and invited members, Discord a group DM's recipients, Messenger and Instagram the participants), so sizes are real counts, except that someone who left a Messenger, Instagram or Signal group without writing is missing from it. A deleted or unknown account keyed by its name ("Facebook user" in Messenger, "Deleted User" in Discord) counts as one person, though it may stand for several, and stays archived itself; the person panel counts a group's people the same way (`SMALL_GROUP_MAX` and `in_small_group` in `modules/friend-map/server/stats.ts`).

That leaves on the map everyone with a name and a direct chat where you both wrote (or, on Discord, where you wrote), everyone from a small group you wrote in, plus everyone you have edited. To bring back someone known only by a number, give them a name or tag them `keep`. "Archive" in someone's panel tags them `archive`; "Unarchive" removes it, and tags them `keep` when a rule would archive them again. Archiving someone in the app (their panel's Archive, or their tag box) shows a chip at the bottom of the page naming them, with Undo for a few seconds: it undoes that archive's changeset (saving tags answers with the changeset it made, `PUT /api/archive/people/:id/tags`), so they come back wherever they showed, or the chip says why it was refused (another tag added since does not stop it; unarchiving and archiving them again since does). It follows the name choice, and with names hidden (No name except…) a refusal leaves out the archive's words, which name people. The same chip shows when a tag is made or deleted, naming it, with Undo for its changeset: a tag created in the tag manager or by typing a new one in someone's tag box, and one deleted in the tag manager or because its last person was taken off it ("as nobody has it now"); the tag manager's changes answer with their changeset (`TagsChanged`), and saving someone's tags with the tags it made and deleted. Each change gets its own chip, stacked with the newest at the bottom, each with its own few seconds and its own Undo; pointing at one, holding it on a touch screen or moving into it with the keyboard holds its time. An older chip's Undo is refused, saying why, when a later change depends on it. At most three show: one more sends the oldest away early, its change still undoable from the change log. A save that archives someone shows the archive, whose Undo takes back the whole save (`src/changeChip.ts`). An open group chat's **Archive untouched** archives at once everyone in it you have never changed (see people.md's "Untouched" under people.md's "People") who is not archived yet, with no question first (the chip's Undo is the safety net), and never takes you, anyone you have changed, or anyone archived already. It is one changeset (`POST /api/archive/groups/:id/archive-untouched`, given who the page showed, and refused with nothing changed when that is no longer who it is), so the chip says "Archived 9 people" and its one Undo brings them all back. Archiving them is a change of yours, so they are no longer untouched, until it is undone. `npm run archive -- people` ends with how many are archived by each rule, and `people --archived` lists them.

**Marketplace.** A chat about something for sale on Facebook Marketplace is marked as one by the `facebook-dyi` connector (the download titles it "<first name> · <item>", with at most two people in it; the phone export has none). Marketplace chats count in nothing: not in message counts, last spoke, trends or the map, and not as group chats. A person's panel says how many Marketplace messages they have, and their timeline shows them only when you tick "Show Marketplace messages". Someone whose only chats are Marketplace ones is archived.

**Dropped group chats.** A group chat that ties together people who don't know each other (a bulk message you sent to many contacts at once, say) can be dropped: `npm run archive -- group drop <#>` (its number from `groups`), a changeset like any edit. A dropped group links nobody and counts in nothing worked out from group chats: not in Orbits' or the map's links, closeness, message counts, last spoke, the archive rules (so it keeps no one as a small group you wrote in), a person's group chats, `groups` or a query's `group:`. Its messages stay in the archive, and the chat itself still opens by its number (`GET /api/archive/groups/:id` and its messages), though no person's panel lists it any more. It is marked on the chat (`conversation.dropped_at`), which imports never write, so importing the same export or a newer one again keeps it dropped. `groups --dropped` lists the dropped ones, and `group restore <#>` (or undoing the changeset) brings one back. There is no button for it in the app yet.

**Taking someone out of a group chat.** Someone added to a group chat by mistake, who never wrote there, can be taken out of it alone: `npm run archive -- group remove-member <#> <person>` (the group's number from `groups`, the person's from `people`), a changeset like any edit. They are then no member of that group in anything worked out from group chats, as if the imports had never listed them: not in Orbits' or the map's links to its people, closeness, the group's size and members, their group chats, the archive rules (so it keeps them on the map as a small group you wrote in no longer), a query's `group:` or the `person_group` view. The group's messages stay. It is refused for you and for anyone who wrote there (a reaction is not writing). It is marked on their membership (`conversation_member.removed_at`, each of their accounts listed there), which imports never write, so importing the same export or a newer one again keeps them out; should a newer export have them write there after all, they count again, by what they wrote. `groups --removed` lists everyone taken out, and `group put-back <#> <person>` (or undoing the changeset) puts them back. There is no button for it in the app.

**Unlinking someone from a group chat.** A group chat can say nothing about who someone knows (a big community chat, say, or one they were added to and ignore): the link button at a group's right in their panel's Group chats (shown when you point at the row) unlinks them from it, and the row keeps a broken-link icon, which links them through it again. They stay in it: its size, its members, their group chats, the archive rules, a query's `group:` and closeness all count it as before (closeness is about how much you talk, not who knows whom). It only connects them to nobody: no link through it when someone is held on the map, Orbits 3D or the City, or in friend circles (Circles and the frozen views' friend groups), and it adds nothing to the "shared group chats" weight between them and its other members, whose links to each other stay as they were. It is kept by person, not account (`group_unlink`), which imports never write, so importing again keeps it, a merge gives the one kept the other's, and it is one changeset (`PUT /api/archive/people/:id/groups/:groupId/unlinked`) with the chip's Undo, in the change log as "group chat: linked through ... / unlinked from ...". The relationships report lists them in `unlinks`, and every view goes by `connectedIds` in `src/archive.ts`.

**People.** Who is who, how accounts are joined into people, proposals, merges and the CLI for them are in "People", above.

**Structure and content are kept apart.** Everything except `timeline`, `search` and `event-content` (see events.md's "The event index") prints names, counts and dates only, and the API under `/api/archive/` never returns message text. Text and attachment files are served only under `/api/archive/content/` (timelines, search, and `GET /api/archive/content/attachments/<id>`), and text is sent only through it (`POST /api/archive/content/conversations/<id>/send`), so a stricter rule can later be put on that path alone. A SQL query never reads content (see queries.md's "SQL queries").

**The trail of content reads.** Every read of content through `timeline`, `search` and `event-content` and the content routes is kept in the `content_read` table of the calendar's file (`server/archive/contentLog.ts`; see events.md's "The calendar"): when, from the CLI, the app or the viewer, who (an agent names itself in the environment variable `LIFE_ARCHIVE_READER`, such as `LIFE_ARCHIVE_READER=codex`, or in `FRIEND_MAP_READER`, its old name; the app's page and the viewer name nobody), what (the command or route: `timeline`, `search`, `event-content`, `conversation`, `day` or `attachments`, with its person, chat, day, search words or event) and why (the captain's words, given with `--why`). The same read again within ten minutes adds to its row, so a history read a page at a time, a chat's photos as they scroll in, or a video seeking, is one row with how many times; a file is kept by its chat. A search that finds nothing is a read too, since whether words are in the archive is content. Your own reads in the app are kept as the app's, and the chats and sessions you open in the viewer's drawer as the viewer's (see console.md's "The viewer"). `npm run archive -- content-log` shows the trail, the latest first; nothing deletes from it.

**Learning the format without content.** `timeline` and `search` take `--json` for the answer as the content routes give it (`TimelinePage` and `SearchHit[]` in `src/archive.ts`), `--redacted` for the same answer with every text (and search snippet) replaced by how long it was (`[redacted: 143 characters]`), and `--testing` for the same command over the testing data instead of the archive (the made-up chats and people `npm run testing-data` makes, with photos, a video, a voice note, reactions and group chats, made afresh in a temporary folder; Ada Sample is person 2). Files are given only by type, MIME type and size either way. A `--redacted` read of the archive is still kept in the trail, marked redacted (what a search matches is content even with its text hidden); a `--testing` read is not, and never opens the archive. A person's timeline comes newest first, 50 messages at a time (the first page as soon as their panel opens, each older one as you scroll near the top), and the panel shows it the other way up, as a chat reads: days and messages oldest to newest (`chatDays` in `src/chatDays.ts`), in its own scroll box that opens at the newest message and keeps your place as older pages or players above load. Opened at a moment instead (the Table's **When**), it loads the page just before the moment (`before=<ms>:0`) and the page just after it (`after=<ms>:0`, newest first like any page, with `nextAfter` for the next newer one), scrolls to what it was opened at, and pages newer messages in as you scroll near the bottom ("Newer messages"), keeping your place; new messages coming in wait until it has paged down to the newest. Each page is a read in the trail as any other. "Load all", beside "Older messages", fetches the rest of the history in pages of up to 5000 (the route's largest; `count=1` adds the `total`), showing "Loading… 12,000 of 74,075" with a Stop button at the top of the box, and keeps your place as they arrive. Only the days in and near the view are drawn, the rest standing in at their measured (or, until drawn, guessed) heights (`dayWindow` in `src/chatDays.ts`), so a history of tens of thousands of messages scrolls as smoothly as one page; the browser's find-in-page therefore sees only the drawn days. It shows photos and GIFs as thumbnails that open full size on a click, stickers whole at their own size (at most 120 pixels), Messenger's like (its thumbs-up sticker, known by its file name) inline at an emoji's size, a bit larger for the medium and large likes, videos and voice messages as players, and other files as links; each loads only when scrolled near or played, and one the export lacked shows as "not in the export". The attachment route serves only files inside `data/platform-exports/` and `data/archive/media/`, with their MIME type and byte ranges so players can seek; types a browser shouldn't open in place are sent as downloads. The server never decodes or inspects the files.

**Telegram, live** (`matrix-bridge`). Telegram reaches the archive as it happens, and you can write back, through the **bridge rig**: the open-source mautrix-telegram bridge and a Tuwunel Matrix homeserver, both built from pinned source and running on this Mac only, on 127.0.0.1, in `~/.local/share/friend-map-bridge-lab/` (its own README says how to start, stop and log in). The archive writes no Telegram protocol code: it logs in to the rig's homeserver as your Matrix user there (on its homeserver, named under `.localhost` so it resolves on this Mac alone, with the password in the rig's `secrets/`, read there and never copied) and reads what the bridge writes, as a Matrix client. Switch it on once, and it runs with the server:

```sh
npm run archive -- enable matrix-bridge       # then restart the archive's server; it reads ~/.local/share/friend-map-bridge-lab
npm run archive -- connectors                 # what it needs, and how the server's copy is doing (live: connected, ...)
npm run archive -- import matrix-bridge       # a one-off read of every bridged chat (sync does this by itself)
```

- **What is read.** Each chat is a Matrix room the bridge made, and the bridge's own record of it (its database's portal table) says which Telegram chat it is (`user:<id>` for a one-to-one chat, `chat:<id>` for a small group, `channel:<id>` for a supergroup or channel); the room's `m.bridge` state says the same, except when the homeserver has given two chats one room, so it only supplies the chat's name. A room the bridge has not recorded yet waits, and is read once it has (looked at again for ten minutes). A one-to-one chat is you and them (your chat with yourself is Saved Messages). Groups of more than 12 people (by Telegram's own count, you included, else the room's members) and broadcast channels are not read at all, by design (big groups only link people together): each is counted once (`chats-not-read-group-of-13-or-more`, `chats-not-read-channel`), and whatever the archive already had from one stays. Everyone is their Telegram user id (the bridge's `@telegram_<id>` users), named as Telegram names them, and a deleted account is "Telegram user"; you are your own id, whether a message came from your phone or from friend-map. Times are Telegram's. Messages, edits (the earlier text is kept), reactions, replies, stickers and files (copied in by content hash) come in; a message deleted on Telegram stays in the archive (deletions are counted, not applied). A call comes in as the bridge's notice for it, from whoever called, which is a **call record** in the chat, as the other apps' are (`telegramCallNotice` in `matrix-bridge/rig.ts` reads its words): "Call ended (12 minutes and 5 seconds)" is a call that long, "Video call missed" (or disconnected, ended or rejected, with no length) one never connected, 0 long; in a group, "Started a video chat" is the group's call, of no known length, and "Ended the video chat (40 minutes)" one that long (the bridge passes on no edit of it, so a video chat seen starting never gets its length). Its notice of a call ringing on you ("Started a call") is a system message from no one, since the call record when it ends is the call. The bridge writes these only for calls made or ended while it runs: it never backfills them, so Telegram's calls from before it was linked are not in the archive. Notices kept as text before this were made calls in place (migration 46), keeping their words and original record. A message's id is Telegram's own, prefixed by its chat (`user:777000/124233`, `channel:1000000001/16537`), read from the bridge's database (opened read-only), so a Telegram Desktop export of the same chats, imported later, can give the same ids.
- **How it follows along.** On its first run it reads every bridged chat from its first message, then follows the homeserver's live sync, a second or two behind Telegram. Each step is applied in one transaction with the point it reached (the cursor), so a restart goes on from there. A new chat (the bridge invites you to its room) is joined and read. If the rig is not running it waits quietly, looking again every minute, and starts when it answers; if it stops, it starts again after 10 s, 1 minute, 5 minutes, then every 30 minutes. After a batch the rules run (at most every 5 s) and open pages follow; a batch that only brings messages updates the counts and the open chat without reloading everyone (see people.md's "People").
- **It never marks anything read.** Any read receipt, read marker, typing notice or presence your Matrix user sent would reach Telegram through the bridge (a receipt marks the chat read on your phone). The connector's one way to the homeserver (`modules/friend-map/connectors/matrix-bridge/client.ts`) refuses every request but logging in, reading, joining a room the bridge invited you to, and sending a text message, and every sync says you are offline; the tests hold it to that.
- **Sending is off for now.** `SENDING` in `modules/friend-map/server/send.ts` is false: the send route refuses every send (409, "sending is turned off in friend-map for now"), whatever is connected, and the person panel has a draft box (see people.md's "Drafts" under people.md's "People") where the composer was. The code below is kept for when it is back: turned on, the composer (`src/Composer.tsx`, then shown again under a person's chat) does as follows.
- **Sending.** The composer under a person's chat (their one-to-one Telegram chat, or Saved Messages in yours) sends a text message when you press Send (or Ctrl/Cmd+Enter), and says how it went: sent, failed with Telegram's reason, or not confirmed. It shows whether Telegram is connected, and is disabled when it is not (the rig not running, the bridge not answering, or logged out of Telegram). The message then comes into the chat like any other, once. Nothing else sends, and nothing is sent by itself: the server's send executor (`modules/friend-map/server/send.ts`) is the only sender, and its route takes requests only from friend-map's own page. Each send is recorded in `outgoing_message` (where, when, how it went; not the text, which is in the message itself). The bridge says how a send went because the rig's bridge has `matrix.message_status_events: true`.
- **How deep the history goes** is the bridge's choice: it fills a chat once, when it makes its room, with up to `backfill.max_initial_messages` of the chat's newest messages, and cannot add older ones to a room that exists (the homeserver has no batch sending). As the rig is set up, that is every chat's whole history, for one-to-one chats and groups of 12 people or fewer; bigger groups and channels are not bridged (by design: they only link people together), so they get no room and nothing new from them arrives, while what the archive already has from them stays. The bridge keeps them out with its deny list (`bridge.portal_create_filter`, by chat id) and `network.max_member_count: 12`, which only catches supergroups: a new small group of more than 12, or a new channel, gets a room when it next has a message, but the connector does not read it (see "What is read"); its id can go on the deny list to spare the bridge the room. To change how deep it goes there is no need to wipe the rig or log in to Telegram again: raise `backfill.max_initial_messages` and `max_catchup_messages`, and `network.sync.update_limit` and `create_limit` (-1 for every chat), in the rig's `config/bridge-config.yaml`, restart the bridge, then send the bridge bot `delete-all-portals` and then `sync-chats` from a room of just you and it; the rig's README has the steps. That only drops and remakes the rig's own rooms; on Telegram it only reads. The connector joins and reads the new rooms by itself, and every message keeps its Telegram id, so nothing already in the archive is doubled. While the bridge fills a room faster than one sync answer holds, the connector reads on from its last answer rather than the whole room again. The bridge's chat sync leaves out chats in Telegram's Archive folder, one-to-one chats with deleted accounts, and chats you were removed from; an archived chat comes in, with its history, when it next gets a message.
- **Another network** (Signal, say) is another mautrix bridge in the rig; the connector reads any bridgev2 bridge's rooms and database the same way, and each needs only a profile (`BridgeProfile` in `matrix-bridge/rig.ts`: its protocol id, user prefix, bot, Matrix device, and how its people, chats and message ids become the archive's) and a connector folder naming its platform, as WhatsApp has (below). Each network's connector logs in as a Matrix device of its own (`FRIENDMAP` for Telegram, `FRIENDMAP_WHATSAPP` for WhatsApp), since logging in again as a device ends that device's other session, and each leaves the other bridge's rooms and invitations alone.

**WhatsApp, live** (`matrix-whatsapp`), read only for now. The rig also runs the open-source mautrix-whatsapp bridge (pinned source, with one local change: nothing friend-map does, joining a chat's room or sending, marks a chat read on your phone), linked to your own number as a WhatsApp linked device ("friend-map bridge lab" under Linked devices on your phone; the rig's `README-whatsapp.md` says how to link, unlink and remove it). The same reader as Telegram's reads it, with the WhatsApp profile, so everything under "Telegram, live" holds, except:

```sh
npm run archive -- enable matrix-whatsapp     # once the rig's WhatsApp bridge is linked; then restart the archive's server
npm run archive -- import matrix-whatsapp     # a one-off read of every bridged chat (sync does this by itself)
```

- **Keyed as `whatsapp-db` keys WhatsApp**, so a message imported from the app's databases and the same message arriving live are one row, and a person is one account either way. The bridge keys most people and one-to-one chats by LID (`@whatsapp_lid-<n>`, `<n>@lid`); the connector turns a LID into the person's phone JID (`61491571266@s.whatsapp.net`, handle `+61491571266`) through the bridge database's LID map (`whatsmeow_lid_map`, read-only), and keeps the LID (`<n>@lid`) only while the bridge does not know the number, as `whatsapp-db` does (at the link, some one-to-one chats may have no number yet: each becomes an empty chat keyed by its LID, since its messages were already in the archive under the phone-keyed chat, with an account that sent nothing, which the rules archive). Someone first seen by LID moves to their phone key for every message after the bridge learns the number; what came before stays under the LID, as a second account of theirs. A one-to-one chat is the other person's key and a group its `@g.us` JID. You are `me`, under your number and your LID alike (from the linked device's own record). A message's id is WhatsApp's stanza id, the last part of the bridge's `<chat>:<sender>:<stanza>` and the id `whatsapp-db` gives the same message.
- **What the bridge writes in place of a message is not its text.** A photo or file whose file WhatsApp no longer has (old history) is that message with its file missing, its caption kept; a contact card (a `.vcf` file) is a contact named as on the card, as `whatsapp-db` has it; and an "unsupported message" notice is a message of another kind with no text (WhatsApp has no notices of its own, so every notice is the bridge's). The first live read, before this, gave 111 imported messages the bridge's words; migration 17 gives them their text back.
- **Names**: the bridge names people from your phone's contacts, else the name they gave WhatsApp, else their number; a number or "WhatsApp user" never replaces a name an import found (see people.md's "People").
- **Not read**: groups of more than 12, you included (by the room's members, all of which the bridge adds), WhatsApp channels, broadcast lists and status updates, and communities (the space that holds a community's groups; its groups are read like any other), each counted once. A call is a system message with no sender ("Incoming voice call…", which the bridge writes itself, only for a call that rings on it), so it never counts as talking, and it is never a call: the bridge passes on no call's length or outcome, and none of WhatsApp's call log (mautrix-whatsapp reads none of it), so WhatsApp's calls come from `whatsapp-db` ("Calls" under "WhatsApp" above). Messages, edits, reactions, replies and files come in as for Telegram; a message deleted for everyone stays.
- **History** comes only when the number is linked: the phone sends about a year (`history_sync.request_full_sync: true` in the rig's `config/whatsapp-bridge-config.yaml`), and the bridge fills each chat's room with up to its newest 10,000 messages; older history comes from `whatsapp-db`. Taking it again means unlinking and linking again (the rig's `README-whatsapp.md`). The phone must come online at least every 14 days, or WhatsApp unlinks it.
- **It never sends.** Its manifest cannot send, so the composer offers no WhatsApp chat, the send route refuses one ("friend-map cannot send on whatsapp"), and the connector itself refuses a send command. It never marks anything read either: the same Matrix client as Telegram's, which cannot send receipts, typing or presence, and the rig's local change covers what the bridge would otherwise mark read on its own.
- The name `whatsapp` no longer picks a connector in the CLI (two serve WhatsApp): name `whatsapp-db` or `matrix-whatsapp`.

To try it without the rig, `node modules/friend-map/fixtures/matrix-rig.ts /tmp/life-archive-matrix` runs a made-up rig with sample chats (and writes that testing data folder's settings), then `LIFE_ARCHIVE_DATA=/tmp/life-archive-matrix/data LIFE_ARCHIVE_URL=http://127.0.0.1:4652 npm start` here and, in friend-map, `FRIEND_MAP_DATA=/tmp/life-archive-matrix/data LIFE_ARCHIVE_URL=http://127.0.0.1:4652 PORT=4612 npm start`.

**Connectors are isolated.** Each runs in its own child process and writes events the archive checks, spools to disk (so an export of any size imports in bounded memory) and applies in one transaction. A connector that crashes, hangs or writes something malformed fails its own import (or, live, its own unfinished batch), leaving the archive as it was, and is marked with the error (`npm run archive -- connectors`); the others are unaffected. If the archive cannot be opened, the archive's routes answer 503 and the page says so.
