# Where the data lives

The archive's folder: what is in it, the platforms' exports and jobs that fill it, and its backups.

## Where the data lives

What is one person's and not code (the time zone, the locale, the machine's addresses and paths) is in `.env.local` and the archive's `settings.json`: `docs/settings.md`, and `.env.example` for every key.

The archive's folder is `~/life-archive-data`, outside every checkout, unless `LIFE_ARCHIVE_DATA` names another; `FRIEND_MAP_DATA`, the name friend-map gave it while the archive was friend-map's, is taken too, after it. Each is read from the environment, then from `.env.local` (gitignored, `KEY=value` lines; a relative path is from the repository, `~/` the home folder), so nothing need be exported, and the first of the two that names a folder decides: `LIFE_ARCHIVE_DATA=/tmp/testing` (or `FRIEND_MAP_DATA=/tmp/testing`) in the environment runs on that folder alone, whatever `.env.local` says (`server/dataHome.ts`). The server, `npm run archive`, `check-data` and the connectors' scripts all find it this way. With nothing named, two checkouts use a `data/` of their own instead: one still holding a real `data/` folder, as the captain's did until the folder moved out, and a linked git worktree, so that an agent's or the pipeline's unlanded code, whose every run would migrate what it opens, never finds the real archive by itself. In these documents, as in the code's comments and messages, the archive's paths are written `data/...` for short, except in commands, which name the folder.

**`data/` is the owner's life archive, and irreplaceable.** It holds everything of theirs this project keeps: the messages and media from their apps, their conversations with agents, everything they have decided about people, and, where they keep one, a link to their Obsidian vault at `data/Vault` (journals, notes and drafts, the journal module's, see features.md's "Journal"; the vault itself can live in iCloud Drive, below). Much of it may exist nowhere else. It is never deleted, cleaned or reset, not even to start over: to try something on a clean archive, point `LIFE_ARCHIVE_DATA` at a scratch folder (see running.md's "Running") and leave `data/` alone. It lives outside the checkout so that nothing done to a checkout (`git clean -x`, a wrong `git add -f`, a worktree tool) can reach it; a copy of this repository that still holds a real `data/` folder has it gitignored, so `git clean -x` or `git clean -X` there would delete it whole. Its other copies are the NAS's nightly backup and Time Machine (see "The NAS copy"); the vault's are iCloud's and Time Machine's.

`data/Vault/` is the owner's own: they edit it in Obsidian, and other tools of theirs may write to it too. This project's code writes to it in one place only: the journal module's voice journals' transcription adds each new recording's copy and raw transcripts under `Journals/assets/` and `Journals/raw/` (see features.md's "Journal"). It can live in iCloud Drive, in Obsidian's own folder there, `~/Library/Mobile Documents/iCloud~md~obsidian/Documents/Vault` (Obsidian's "iCloud" vaults, which a phone's Obsidian opens), with `data/Vault` a link to it, so every path that names `~/life-archive-data/Vault/` reaches it unchanged.

- **Its backups are then iCloud's and Time Machine's, not the NAS's**: the nightly backup leaves `Vault` out (`ARCHIVE_EXCLUDES`). Time Machine includes `~/Library/Mobile Documents`, but it backs up only what is downloaded on the Mac, so with iCloud's "Optimise Mac Storage" on, set the folder to Keep Downloaded in Finder (Control-click it, Keep Downloaded): macOS then never evicts it, which any tool that writes to it needs too. Finder is the only supported way to set that; the folder carries the extended attribute `com.apple.fileprovider.pinned` while it is set (`xattr -p com.apple.fileprovider.pinned <folder>`).
- **A program that launchd runs** needs macOS's permission to reach files iCloud Drive keeps ("would like to access files managed by iCloud Drive", the TCC service `kTCCServiceFileProviderDomain`), given to each program by its path: without it a launchd job cannot list the vault's folders. Each Node version is a program of its own to macOS, so a new one asks again the first time its job reaches the vault, and the job waits until someone answers.
- **Two writers at once**: when a phone and a tool on the Mac change the same note before iCloud has synced, iCloud keeps both, the second as `<note> 2.md`.

### Platform exports

Every export lives in `platform-exports/<platform>/<export date>/` in the archive's folder, as it came: put the zip (or a Meta download's zip parts) there, unpack it in place, and import that folder. The archive copies messages into `archive.sqlite` but never media: each attachment (`attachment.local_path`, named relative to the archive's folder) points at the file itself in the export, so there is one copy of it, and a file lasts as long as its export is kept. Media with no export behind them, which a live bridge downloads (Telegram, WhatsApp live), are copied into the platform's `live/` folder there, named by content hash. So one folder per platform holds all it has, and `npm run archive -- storage` says how much: in all, and per platform its messages (its share of `archive.sqlite`), its exports (the zips, and what they unpacked to), the media pointed at, and old copies nothing points at.

```sh
mkdir -p ~/life-archive-data/platform-exports/messenger/2026-10-06/ && mv ~/Downloads/facebook-*.zip ~/life-archive-data/platform-exports/messenger/2026-10-06/
npm run archive -- exports unpack ~/life-archive-data/platform-exports/messenger/2026-10-06/    # unpacks every zip there, keeping the zips
npm run archive -- import facebook-dyi ~/life-archive-data/platform-exports/messenger/2026-10-06/
npm run archive -- storage
```

`exports unpack` writes each file of each zip at the top of the folder into the folder (a zip stored inside a Meta part too), checked against the zip's checksum, through a temporary file, and never over a file already there, so it can be run again; the first part's copy of a file that several parts carry is kept, as the import would read it. A connector refuses an export whose media are still in a zip, saying to unpack it; a zip holding no media (Discord's package, an X archive without photos) can still be imported as it is. The export folder's name is the day it was made (YYYY-MM-DD; a second the same day can be `2026-10-06-2`), since that orders them.

**A second export of a platform** (a newer download, or one covering a later stretch, as a Messenger download from the 24th of September on continues one made on the 28th) is imported the same way, into its own dated folder: its new messages are added, those both exports have are kept once (every connector gives a message the same id in any export of it), and each attachment points at the file in the newest export holding it (by the folders' dates: an export over the live folder, a later export over an earlier one, whichever was imported first), so the newer download's photo of a message replaces the older's, and importing the older one again changes nothing. A message the archive matched across two connectors (Messenger's phone export and Facebook's download, see archive.md's "The same message from both") keeps the attachments of the one imported first.

Before `platform-exports/`, connectors copied media into `data/archive/media/<platform>/` and exports waited in `data/imports/<platform>-<date>/`. To move to this layout, with the server stopped and a backup taken:

```sh
npm run archive -- exports move-imports            # where each export in ~/life-archive-data/imports/ goes; --apply moves them, renames only
npm run archive -- media repoint                   # the dry run: what re-points, per platform; --apply makes it
```

`exports move-imports` renames each `data/imports/<platform>-<date>/` to `data/platform-exports/<platform>/<date>/` (the device in its name dropped: `whatsapp-iphone` is `whatsapp`, `signal-desktop` is `signal`, and the iPhone's address book `addressbook`), or moves its entries into that folder when it is there already; an entry already there blocks only itself. It points the imports' recorded sources at the new places. `media repoint` finds, for each attachment still on a copy in `archive/media/`, the file in its platform's exports with the same size and SHA-256 (the newest export holding it; the copy is checked against the same), and points the attachment there; an attachment a live bridge brought that no export holds gets a copy in the platform's `live/` folder (a clone, which takes no space while the copy stays) and points there. What cannot be matched stays on its copy, said why. `--apply` logs every change to `data/archive/repoint-<time>.jsonl` and changes each attachment only if it still points where the dry run found it. Nothing is deleted, neither a copy nor an export: it ends with the copies in `archive/media/` that nothing points at any more, and how much space they hold, for the captain to delete, or keep.

The server serves attachments only from `platform-exports/` and `archive/media/`, whatever a stored path or a symlink says (`server/archive/mediaPaths.ts`).

### Exports from the Cua Space

Instagram's and Facebook's messages, Messenger's end-to-end-encrypted chats and Discord's data package are asked for, waited on and downloaded by an agent in a Cua Space (a macOS virtual machine on this Mac, from Cua Spaces), and taken into the archive on the Mac by `npm run cua-exports` (`modules/friend-map/jobs/cua-exports.ts`, `cuaExports/` beside it). docs/import-runbook.md's "Computer-use help" has the captain's part.

- **In the Space.** Each round is a Codex run the Mac starts in the Space (`cua agent run`, labelled as `cua.agent` in the settings says, `LIFE_ARCHIVE_MODEL`), using the Space's own `~/.codex`, where Codex is signed in with a ChatGPT account (no API key); it stops by itself when the round's turn ends. It is not a persistent Cua agent: one keeps Codex's home in the Cua Volume, where Codex cannot start (its SQLite state fails there with "Operation not supported", and Cua cannot link the sign-in into it), and where every version of the sign-in and of the agent's session logs would be kept for good. Each round it reads `plan.json` and does what `PLAYBOOK.md` (`modules/friend-map/jobs/cuaExports/agent/`) says, in the Space's own Chrome, in the profile `friend-map-exports`, where each site is signed in to once. It drives that Chrome through the Mac, not with the Space's own driver tools (the browser bridge, below), so that the Mac's Cua Keyvault can fill Meta's password box in it. It reports each thing that happened as one line of `events.jsonl`, written by `event.sh`: a request made, an export still being prepared, one downloaded (each file's name, size and SHA-256), a stop for the captain, a platform's "not before" day, a failure, and the round's end. These files are in the Space's folder of the Cua Volume, `spaces/<the Space>/friend-map-exports/`. The Volume is stored on this Mac only (Cua's `fs` store, in `~/.cua/volume`), but it keeps every version of every file it is given, so the exports never go through it: they wait in the Space's Downloads until the Mac takes them.
- **How often.** Instagram and Facebook: a request each week, Messages only, JSON, higher quality, from the day before the archive's imports reach (import-status's "covers to") to the day before today: the Space's Chrome keeps US Pacific time, which can be up to a day behind the archive's time zone, and Meta's date picker will not save a range ending after the browser's own today, which early in the archive's day can still be the archive's yesterday. Messenger's encrypted chats: each 30 days, the whole of their secure storage, downloaded on messenger.com while the page waits (each is the whole history, which can be large, so monthly; Facebook's weekly export has every chat that is not encrypted). Discord: each 30 days (its own limit), Messages only. A request is checked each day until its export is downloaded (Meta keeps a ready export for about four days), and asked again when it lapsed (expired, cancelled, or nothing after 30 days). `plan.json` says what is due.
- **The browser bridge.** Meta asks for the password again at Start export and at Download (Facebook's and Instagram's Accounts Center, and messenger.com's secure storage). The Cua Keyvault fills a saved password only into a browser the Mac's Cua drives: cua-driver gives a browser, its tabs and its session to the connection that launched it, so a Chrome the round's Codex launched with the Space's own driver tools cannot be read or typed into from the Mac ("session is not available to this transport"; "browser_endpoint_owner_mismatch"), and the Keyvault fills from the Mac, through the Cua daemon, whose connection every `cua` process here shares. So each round is started without the Space's own driver tools (`--no-sandbox-mcp`) and with the bridge's in their place, under the same name (`--mcp cua_driver=...`): `npm run cua-exports -- bridge` (`modules/friend-map/jobs/cuaExports/bridge.ts`), kept running by the launchd agent `local.life-archive-cua-bridge` (log `~/Library/Logs/LifeArchive/cua-bridge.log`). It is an MCP server on the Mac's address on the Space's network (192.168.64.1, the port `CUA_BRIDGE_PORT` names, 4656 unless said), at a path holding a random token that `setup` makes once and keeps in `platform-exports/.cua-exports.json`, so only the round, given that address, reaches it. Each call goes on to the Space's driver through `cua mcp` (a process of its own each time). It offers the round the browser's tools and no others (`browser_prepare`, `list_windows`, `get_browser_state`, `browser_navigate`, `browser_click`, `browser_type`, `browser_pointer`, `browser_dialog`), each in one session, `friend-map-exports`, which it starts again (`start_session`) when a call finds it ended: the bridge runs for days, anything may end that session (a probe's clean-up once did, and the next morning's round was refused `session_ended`), and the driver revives an ended session only on `start_session`; `browser_prepare` always opens the export profile; every snapshot is `semantic_v2` (a `dom_refs_v1` snapshot's labels can carry what was typed into a box, a password the Keyvault filled among them). And `request_site_login`, for a tab on one of Meta's origins alone (`accountscenter.facebook.com`, `www.facebook.com`, `m.facebook.com`, `accountscenter.instagram.com`, `www.instagram.com`, `www.messenger.com`; the bridge reads the tab's address itself): the Keyvault files a request, which the captain approves in Cua with Touch ID (each time, until that login is unlocked in Cua: Keyvault > All Items > the login > its lock), then types the saved login for the page's exact origin into the box through the Space's driver and presses its submit button. A login he unlocked is granted at once, but the call that files the request still answers pending, so the bridge waits up to 15 seconds on a new request before it answers: the round hears `pending`, and reports an approval, only when he is really asked. An expired request (he did not answer within the Keyvault's 10 minutes), which Cua words as declined ("do not ask again"), reaches the round as `expired`, and it asks again within its 45 minutes. The password never passes through the bridge, the agent or any log; the bridge logs only a failed tool's name and code, and each Keyvault request's origin and outcome. A login is saved in the Keyvault per origin (Facebook's under `www.facebook.com`, `m.facebook.com` and `accountscenter.facebook.com`, say), and a box on an origin it holds none for stays a stop for the captain until one is imported (`cua keyvault import-passwords --site <site>`, with Touch ID).
- **On the Mac.** `npm run cua-exports` (`modules/friend-map/jobs/cua-exports.ts` and `cuaExports/`, the friend map module's; the agents installed before the module run `server/cua-exports.ts`, which hands on to it until they are reinstalled) runs every 15 minutes (the launchd agent `local.life-archive-cua-exports`, logging to `~/Library/Logs/LifeArchive/cua-exports.log`). Once a day, from the schedule's time (10:00 unless `setup --at` says otherwise) while the schedule is on, it starts the day's round, unless one is still running. It reads the agent's events, each checked first: a line that is not exactly an event is refused, and a download's file names must be that platform's export's. It sends firstmate a note for each new one. It takes each download out of the Space (`cua sandbox cp`) into `platform-exports/<platform>/<day>/`, checks each file's SHA-256 against the agent's, removes the Space's copy, and imports it the runbook's way (`exports unpack` for Meta's, `backup before-import-<connector>`, the import, `check-data`). Then it writes the next plan. Before it starts a round it checks the bridge answers, and starts none while it does not. What it has done, and its schedule (the Space, the time, on or off, the model), are in `platform-exports/.cua-exports.json`, so each note is sent, each export taken and each day's round started once; a download whose copy does not check out stays in the Space and is tried again next run.
- **Telling firstmate.** Notes go through firstmate's inbox (`bin/fm-inbox.sh note --request-id`, in `FIRSTMATE_HOME`; a macOS notification where there is none): a request made, an export imported (its message count and what `check-data` said), a stop for the captain (which kind, and where to do it), Meta's password box re-entered from the Keyvault (handled: nothing for him), a Keyvault request waiting for his approval (its id), a platform's "not before" day, a failed round, Signal's export due on the captain's Mac (once its imports reach back a week, and each week after: Signal Desktop's export cannot run in a virtual Mac, which has no Secure Enclave for its presence check), a round whose run Cua says failed or that ended without reporting its end, and the agent silent for two days while the schedule is on (Codex signed out in the Space, or the Space stopped). Each note is worded on the Mac from the event's checked fields. The agent reads web pages, so its own words are never passed on; `npm run cua-exports -- status` shows them. Each stop also raises a macOS notification on the Mac, at the same 15-minute run (a round has no way to notify the Mac itself).
- **The captain's part.** Once: sign Codex in inside the Space, and sign in to Instagram, Facebook, messenger.com and Discord in the agent's Chrome profile, which **Export browser** on the Space's Desktop opens at the four pages (`modules/friend-map/jobs/cuaExports/agent/Export browser.command`, put there by `setup`). That profile's folder is `~/Library/Application Support/CuaDriver/BrowserProfiles/friend-map-exports` in the Space; Chrome from the Space's Dock opens Chrome's default folder, which the rounds cannot use (Chrome refuses to be driven there), and Chrome sync carries no site's sign-in, so it is not needed; then quit that Chrome, since a round cannot use the profile while it is open by hand (the round says so, as a stop, and never closes his window). After that, only the stops: a sign-in that expired, a code, a captcha, Meta's "Was this you?", Messenger's secure storage PIN (once for this browser, as for any new device), an identity check, and each Discord package's emailed link, which he opens in the Export browser. The password Meta asks for again at Start export or Download is not his to type: the round has the Keyvault fill it (above), so all he does is approve the Keyvault's request in Cua with Touch ID until the login is unlocked there, after which it needs nothing from him; it is a stop only where the Keyvault has no login for that page, or he declined. At a stop the agent leaves its Chrome window open and waits up to 45 minutes for him to clear it on the Space's screen (the Cua app's viewer, or `cua sandbox view <the Space>`); later, he does it in the Export browser and runs `npm run cua-exports -- nudge`, or leaves it to the next day's round. The round never types a password itself: only the Keyvault does, and the round asks it only for Meta's password box.

```sh
npm run cua-exports -- setup --space <id>   # the playbook into the Volume, Export browser onto the Space's Desktop, the schedule (off until --enable), the bridge's token; run again, it changes
                                            # only what its flags name: --at HH:MM, --model, --enable or --no-enable, --rehearse (stop before Start export) or --no-rehearse.
                                            # It also retires the first design's persistent agent and its routine, if they are there
npm run cua-exports -- install              # the two launchd agents, the run every 15 minutes and the bridge (from the checkout whose archive takes the exports); --dry-run prints them
npm run cua-exports -- status               # the schedule, whether the bridge answers, the latest rounds and Cua's word on each, the settings, the plan, the latest events, the imports
npm run cua-exports -- nudge                # a round now, after the captain cleared a stop (refused while one is running)
npm run cua-exports -- --dry-run            # what a round would do, doing nothing
```

### This Mac's calls and Messages, every 15 minutes

`call-history` and `imessage-db` are copied from this Mac and imported, named from the Mac's Contacts, with no import session: `npm run mac-imports` (`modules/friend-map/jobs/mac-imports.ts` and `macImports/`, the friend map module's; `server/mac-imports.ts` is the old path, kept so the launcher installed before the module still runs, handing on to the module's, `server/handOn.ts`). Every 15 minutes, and that is both sources' only schedule: a source has one sync slot, so nothing runs them weekly. The launchd agent runs it every 15 minutes and when it is loaded (launchd starts it only when it is not still running, and a run's lock, `mac-imports/lock` in the archive's folder, keeps one started by hand from overlapping it). It does what docs/import-runbook.md's "From this Mac" does, in code, for what is new only:

- **Whether anything is new.** Each run asks each database for its newest row's id (the call history's `ZCALLRECORD.Z_PK`, Messages' `message.ROWID`; both only ever grow) and compares it with the one its last import copied, kept in `mac-imports/state.json`. When neither is higher the run is done: it copies, backs up, imports and notes nothing, and logs one line. A call or message changed later (an edit, or an attachment that downloads after its message) comes in with the next new one, since every import reads the whole copy.
- **The address book.** People are named from the Mac's Contacts, which iCloud keeps in step with the phone, rather than from an iPhone backup's address book. Each store in `~/Library/Application Support/AddressBook/` (the Mac's own `AddressBook-v22.abcddb` and each account's under `Sources/<id>/`) is copied into `platform-exports/addressbook/<day>/`, at the same paths and the same way as the databases below, the cards' photos left, by a day's first import; the day's later imports use that copy, so a card added on the phone names its person by the next day's. When that copy fails, the newest address book there before is used. `modules/friend-map/connectors/addressBook.ts` reads either kind (see people.md's "Notes" under People).
- **The copies.** For a source with something new, `CallHistory.storedata` (`~/Library/Application Support/CallHistoryDB/`) into `platform-exports/calls/<day>/`, and `chat.db` (`~/Library/Messages/`) into `platform-exports/imessage/<day>/`, each with SQLite's backup from a read-only connection, as `sqlite3 -readonly ... .backup` makes it; beside `chat.db`, the files under `~/Library/Messages/Attachments/` changed since two days before import-status's "covers to" for `imessage-db` (every one when it has never been imported), with their times, as APFS clones. A day keeps one copy of each: a later run that day brings the same folder up to date (the database replaced by the newer one, attachments added, none taken away, so what earlier imports point at stays), since `chat.db` alone is about 100 MB and a copy for every sync would fill the disk. Each copy is made under a hidden name (`.copying-<day>`) and moved in when whole; a `<day>` folder the job did not make (one copied by hand) is left, and the job's goes in `<day>-2`. Nothing reads a message or a call: a database goes page by page, a file by its name and time, and the newest row's id is all that is read of either.
- **The imports.** One `backup before-import-mac-imports` before a run's imports (the archive is over a gigabyte, so the run's earlier one that day is deleted: a day keeps one, the restore point before its latest import), then each import with `--contacts` that address book (without one, people show by their numbers), then `check-data` once. check-data runs here after every import, and nowhere else on a schedule.
- **Telling firstmate**, through firstmate's inbox as for the Cua Space's exports, rarely: the first run of a day notes what came in on the days before (`2026-11-02: 3 calls and 12 messages (2 attachments), in 4 syncs; check-data found nothing wrong.`), and nothing when nothing did. A copy, backup or import that fails is noted at once, with which step and where its copy is, to import by hand from the backup step, and so are problems `check-data` names; each once a day. After a failure the next try waits an hour, so a failing import is not copied and backed up every 15 minutes. A run that fails logs an ERROR line and raises a macOS notification, the day's first only. The import's own error stays in the log, `~/Library/Logs/LifeArchive/mac-imports.log`.
- **Full Disk Access.** macOS lets a process read the three databases only with Full Disk Access (checked for Contacts on this Mac: opening its stores from a launchd job without it fails with "Operation not permitted"), and gives it to the program launchd starts and everything that program starts. Granting it to node would give it to every launchd agent that runs node, the archive's server among them. So the launchd agent `local.life-archive-mac-imports` runs a launcher of its own (`server/launcher.c`), and the grant goes to it alone. It runs one command, `node --no-warnings modules/friend-map/jobs/mac-imports.ts run` in this checkout, with both paths built in (one built before the friend map module runs `server/mac-imports.ts`, which hands on; reinstalling builds a new launcher, whose grant must then be given again). `install` builds it at `~/Library/Application Support/LifeArchive/life-archive-mac-imports`, outside any checkout, and signs it ad hoc. macOS knows it by its signature's hash, so `install` replaces it only when the source or paths changed, and then says the grant must be given again (the schedule is in the agent's plist, not the launcher, so changing it needs no new grant). Until the grant is given, a run reads nothing and notes firstmate once that day, saying what to grant. The run's own processes (node, the archive's commands) have the access while it lasts.
- **The captain's part, once.** System Settings > Privacy & Security > Full Disk Access; click +, press Cmd-Shift-G, paste `~/Library/Application Support/LifeArchive/life-archive-mac-imports`, choose Open, and check its switch is on. It runs within 15 minutes, or `launchctl kickstart gui/$(id -u)/local.life-archive-mac-imports` runs it now.

```sh
npm run mac-imports -- install              # builds the launcher, writes and loads the launchd agent (from the checkout whose archive takes the imports), says what to grant; --dry-run prints it
npm run mac-imports -- --dry-run            # what a run would do, doing nothing (run from a terminal, it reads with the terminal's own access)
launchctl kickstart gui/$(id -u)/local.life-archive-mac-imports    # a run now, as launchd runs it
```

### Backups

Before changing data, take a backup of the core's database and the modules' databases (friend map's archive among them):

```sh
npm run archive -- backup before-tag-cleanup    # ~/life-archive-data/backups/2026-09-29T153000-before-tag-cleanup.sqlite (core.sqlite), and ...before-tag-cleanup.archive.sqlite (friend map's), ...exercise.sqlite
npm run archive -- backup --prune --dry-run     # what the prune would delete; without --dry-run, delete it
npm run archive -- migrate                      # bring every database's schema up to date, after a checked backup when one is behind, and say what changed
npm run archive -- migrate friend-map-module    # the one-time move of an archive from before friend map was a module (a dry run; --apply makes it)
npm run archive -- migrate module-data          # the one-time move of the modules' files into their folders (a dry run; --apply makes it, below)
```

**The modules' files, moved into their folders.** Before each module kept its files in its own `modules/<id>/`, health kept its records in `health/` and exercise its settings in `exercise.json`, both at the folder's root. Each module declares the move (`sdk/server.ts`'s `moves`; `server/modules/moves.ts`) and reads each file at its new place once it is there, else at its old place while it is there, so an archive goes on unchanged until its owner moves them, and the server says at each start what is still at an old place. `npm run archive -- migrate module-data` says what it would move; with `--apply` it copies each old file or folder whole into `data/backups-kept/<date>T<time>-before-module-data/` (never pruned), checks the copy byte for byte, and only then renames it into the module's folder, one rename each, so a file is never in two places nor in none. The server may keep running: both modules read these files afresh each time. A file at both places is refused, with nothing moved, until one is put aside by hand; run again, it moves what is left. To undo, move them back by hand (or from the copy).

Every CLI command that changes people takes one first, named `before-<what it does>` (see people.md's "Changing data from a chat"). A backup is a consistent copy made with SQLite's `VACUUM INTO` (safe while the server is running), named by the local date and time and the label, and checked with `pragma integrity_check`: a copy that fails is removed and the command fails. The command prints the copy's path and size, then prunes: every backup older than 48 hours is deleted, and of the rest only the newest of each local day and every one labelled `before-import-…` are kept (the one just written always stays). So an import session that takes a backup before each import keeps them all for 48 hours, a restore point between each import and the next (about 1 GB each). The server prunes once when it starts, so old backups expire even when no new one is taken. The prune only touches files in `data/backups/` named like a backup; anything else, such as older hand-made `archive.sqlite.bak-*` copies, is left for you. These are short-term safety copies, not a replacement for backing up the archive's folder elsewhere (see "The NAS copy"), and they hold `core.sqlite` and each module's database (`modules/<id>/<name>.sqlite`: a checked copy beside the core's, under the same stamp and label with its file's name after them, `<date>T<time>-<label>.archive.sqlite` for friend map's archive, `.exercise.sqlite` for exercise's, kept or pruned with it as one backup). To restore one, stop the server and put each copy back where it came from: the stamp's `.sqlite` as `core.sqlite`, its `.archive.sqlite` as `modules/friend-map/archive.sqlite`, and so on, after moving the current files and their `-wal` and `-shm` aside. A backup from before friend map was a module (`…-before-friend-map-module.sqlite` among them) is the whole archive as it was: it goes back as `archive.sqlite` at the folder's root, with `core.sqlite` and `modules/friend-map/archive.sqlite` deleted and the code from before started (`server/archive/migrate.ts` says so). The calendar is not in them, which the NAS's nightly backup sends as a checked copy (see "The NAS copy"), and the archive's copies of the agents' conversations (`llm/`) are in no backup of the archive's, since nothing the archive does ever shortens or overwrites them (see events.md's "Conversations with agents, live"); what keeps them should the disk fail is the NAS's nightly backup of the archive's folder, and Time Machine's. The same holds for `transcripts/` (see "Every LLM transcript").

People used to be kept in Markdown person files, in `data/friends/` and `data/people/`, and the retired canvas in `data/canvas.json`. None of these is read any more; see people.md's "Moving the person files in" for what happened to them.

### The NAS copy

The archive's folder lives on this Mac. Time Machine can copy it to a drive of the owner's, and `data/backups/` keeps 48 hours of the databases. The NAS keeps the other copy: an encrypted snapshot of the whole folder each night, made with [restic](https://restic.net/) (`npm run nas-backup`, `server/archive/nasBackup.ts`). Just before it, the same job takes every LLM transcript into the folder's `transcripts/` (see "Every LLM transcript"), so each snapshot holds that night's; and just after it, a second snapshot of `transcripts/` and `llm/` alone, which is never forgotten (see "The transcripts, kept for good", below). The folders `nasBackup.folders` names (below) go into the same snapshot, so one policy covers them all: same night, same retention, same check; rituals' store is in the archive's folder since rituals became a module (see features.md's "Rituals").

**Where it goes, and who can read it.** The backup is a restic repository on the NAS, in the folder `nasBackup.repository` names under the ssh user's home, reached over sftp. restic encrypts everything on this Mac before it leaves (AES-256, with a key that only the repository's password unlocks), so the NAS holds only encrypted files: anyone else with access to the NAS, or to its disks, sees file names like `data/3f/3fa9…` and their sizes, and nothing of what is in them. That also means the folder can't be browsed on the NAS; a snapshot is read through restic (see "Restoring").

**The password.** `npm run nas-backup -- init` makes a long random password (32 random bytes), keeps it in this Mac's login Keychain as a generic password (service `life-archive-backup`, account `life-archive`), and makes the repository with it. It is never printed, written to a file or the log, or committed. Each run reads it from the Keychain itself: restic is given `RESTIC_PASSWORD_COMMAND=/usr/bin/security find-generic-password -s life-archive-backup -a life-archive -w`. `init` never replaces a password already in the Keychain, and on a repository already there it only checks that the password opens it.

**Keep a copy of the password in your password manager.** If the Mac is lost, the Keychain goes with it, and the backup can only be read with that copy. **Without the password the backup can never be read, by anyone**: restic has no way back in. To see it once and copy it:

```sh
security find-generic-password -s life-archive-backup -a life-archive -w   # prints it; macOS may ask for your login password first
```

or open Keychain Access, search for `life-archive-backup`, open it and tick "Show password".

**What a snapshot holds.** Each snapshot is the archive's folder as it was that night, at the snapshot's root, with the folders `nasBackup.folders` names beside it:

- `core.sqlite`: a consistent copy made with `VACUUM INTO` in `data/backups/nas/` and checked with `pragma integrity_check`, as the backups are (see "Backups"). The live file and its `-wal` and `-shm` are never sent. The local copy is deleted once restic has it. (A snapshot from before friend map was a module holds the whole archive as `archive.sqlite` at its root instead.)
- `calendar.sqlite`: a checked copy made the same way, as the live file never is: its events could be rebuilt from the archive, but the trail of content reads in it could not (see events.md's "The calendar"). `npm run nas-backup -- verify` checks it with the others.
- `modules/`: the modules' folders, taken as a mirror built for the night in `data/backups/nas/` (hard links to the live files, which cost nothing, `server/archive/nasMirror.ts`), so each module's database goes into it as a checked copy at its own path: `modules/friend-map/archive.sqlite` (friend map's archive), `modules/exercise/exercise.sqlite`, each `modules/<id>/<name>.sqlite` the core opens for a module, made the same way. A restore puts each back where it lives (below). `verify` checks each with the others. The mirror is deleted after the run; deleting it deletes only the links.
- `modules/rituals/data/ritual.sqlite3`: rituals' store (which rituals' own code keeps, not the core: the rituals module says what of its folder the NAS takes, `backup` in its `module.ts`), a checked copy made the same way, at its own path in the mirror too. `verify` checks it with the others. A module's folder may name any database it keeps itself this way, and the folders of its own to leave out. An installed module that does not load (a folder under `modules/` with no `package.json` counts) stops `npm run nas-backup` and its `verify`, since only its declaration says what of its folder to copy and leave out: no snapshot is made that night, of anything, rather than one that sends a live database; the run says so in a notification, the status file and the storage report's NAS line, and `verify` in its log and exit code.
- Everything else in the folder: `platform-exports/`, `llm/` (the archive's copies of the agents' conversations), `transcripts/` (every LLM transcript, as its tool wrote it), `history/` (the folder history's git repositories, see events.md's "Folder history": so a watched Drive folder goes into the same nightly snapshot and the same week of retention, with its whole history inside each), `archive/`, `connectors/`, `backups-kept/`, `analysis/`, `exports/`, `imports/`, `modules/` (each module's files: rituals' `data/exports/`, `data/views/` and `queue/` among them), and any folder added later, all without being named.
- Left out: `backups/` (the 48-hour copies), `archive/.spool/` (a running import's scratch), `core.sqlite*`, `calendar.sqlite*` and `modules/*/*.sqlite*` (sent as the checked copies instead), what a module says to leave out (rituals' own `modules/rituals/data/backups/`, its copy before each write, and its live `ritual.sqlite3` and `-journal`, sent as the checked copy instead) and `Vault` (the owner's Obsidian vault, a link into iCloud Drive, which with Time Machine keeps it; see "Where the data lives") (`ARCHIVE_EXCLUDES`).
- Each folder `nasBackup.folders` names, at its path (below), less what its entry excludes.

Snapshots made before friend map was a module hold the archive as `/archive.sqlite` and each module's database at the root by its name (`/exercise.sqlite`, `/ritual.sqlite3`), each to be moved back into its folder by hand when restored. The NAS backup refuses to run on an archive's folder from before that move (`archive.sqlite` at its root), saying to run `npm run archive -- migrate friend-map-module`, since its snapshot would leave the archive out. Snapshots made before rituals became a module hold rituals' folder as `/Projects/rituals/data/` (with its `ritual.sqlite3` at the root, as now); the archive's own entries are where they were, so the night after a move read nothing of them again, and the retention counts the old snapshots and the new as one.

Another folder is added with an entry in `nasBackup.folders` in the settings (`docs/settings.md`). It goes into each snapshot under its path from the folder it shares with the archive's (`~/Projects/old-app/data` as `/Projects/old-app/data`, `~/Notes` as `/Notes`, folders under one parent sharing it); a SQLite database in it can be named, to be sent as a checked copy at the root under its own name; and a name already taken there is refused. A folder named there that is missing fails the run.

restic splits files into chunks and stores each chunk once, compressed, so a night costs only what changed since any earlier snapshot. The database copy is mostly chunks already stored, so it costs far less than its 1 GB.

**What is kept.** After each successful run, `restic forget --tag life-archive --keep-daily 7 --prune` keeps the newest snapshot of the archive's folder of each of the last 7 days that have one, so about a week back, and deletes the data only the forgotten snapshots held. A file deleted or damaged on the Mac can be got back from the NAS for that week. Two runs on one day keep only that day's later one. Older history comes from Time Machine, where it is used, restored by hand through the Time Machine app. The transcripts' snapshots are the exception: the forget names only the archive's folder's tag, so none of theirs is ever forgotten, and the prune keeps every chunk one of them holds.

**The transcripts, kept for good.** Every LLM transcript the archive keeps (`transcripts/`, see "Every LLM transcript") and its own copies of the agents' conversations (`llm/`, Grok Bot's chats among them; see events.md's "Conversations with agents, live") are taken again each night, after the archive's snapshot, as a snapshot of those two folders alone, tagged `llm-transcripts` (`TRANSCRIPTS_TAG` and `TRANSCRIPT_FOLDERS` in `server/archive/nasBackup.ts`). Each is at the snapshot's root, as in the archive's (`/transcripts/claude-code/...`, `/llm/grok-bot/...`). These snapshots are never forgotten: every night's state of the transcripts stays on the NAS for good, whatever later happens to the Mac's copy, a file lost or damaged there included, long after the archive's week. It is one repository with one password and one job, so the Keychain, the lock, the fallback to the tailnet, the log and the warnings all cover it.

- **What it costs.** The two folders are in the archive's snapshot too, so restic already holds their chunks: the second snapshot adds only its own list of files and what changed since the archive's: a few megabytes, in seconds, even for the first. What changes is that the NAS keeps everything the folders ever held, which, since both only ever grow, is about what they hold on the Mac, growing as they grow, plus each night's indexes, a few hundred MB a year.
- **Its time.** It is stamped a second before the night's archive snapshot, so `latest` (in `restic restore latest`, `restic ls latest` and `restic mount`'s `snapshots/latest/`) is always the archive's folder. Name `--tag llm-transcripts` for the transcripts': `restic snapshots --tag llm-transcripts` lists every night's, and `restic mount` shows them under `tags/llm-transcripts/`.
- **When it is missing.** A night whose archive's folder has neither folder makes none, and says so. A run whose transcripts' snapshot fails fails whole, as the archive's does: an `ERROR` line, a notification, and no forget that night. `npm run archive -- storage` says how many there are and the first's and newest's days ("none yet of the transcripts" until the first), and `verify` fails while there is none (below).
- **Kept for good means everything in them**, a secret a tool printed included. The fix for a leaked key is to rotate it, not to delete transcripts. If something must really go, `restic rewrite --tag llm-transcripts --exclude <its path> --forget` followed by `restic prune` removes it from the NAS (and the same on `--tag life-archive` for the week's), after it is gone from `transcripts/`; Time Machine's copies would still hold it.

**When it runs.** The launchd agent `local.life-archive-nas-backup` runs it at 06:00 each day, the transcripts' pass first. If the Mac was asleep then, launchd runs it on waking, and `caffeinate -i` keeps the Mac awake until it ends. It reaches the NAS at the ssh hosts `nasBackup.hosts` names, each tried when the one before does not answer (`~/.ssh/config`). It needs restic (`brew install restic`; written and tested with 0.19.1, and each run logs the version it used) and refuses with that instruction when it is missing. It logs to `~/Library/Logs/LifeArchive/nas-backup.log`, one timestamped line per step. A run that fails:

- writes an `ERROR` line to the log;
- raises a macOS notification;
- exits 1;
- is kept in `data/backups/nas-backup.json`.

`npm run archive -- storage` ends with when the last snapshot was made and any failure since, and says "overdue" after two days without one. Two runs never overlap (`data/backups/nas/.lock`). A run stopped with SIGTERM or Ctrl-C stops restic, deletes its database copy and lets the lock go before it ends. A lock a killed run left in the repository is cleared with `restic unlock` at the start of the next, which removes only locks whose process is gone.

```sh
npm run nas-backup -- init               # once: a new password into the Keychain, and the repository on the NAS
npm run nas-backup -- install            # writes ~/Library/LaunchAgents/local.life-archive-nas-backup.plist and loads it (from the checkout whose archive it backs up)
npm run nas-backup -- install --dry-run  # prints the plist instead
npm run nas-backup -- --dry-run          # the transcripts the pass would take, the folders and databases tonight's snapshot would take, how many files it and the transcripts' snapshot would add, and which snapshots would be forgotten; writes nothing
npm run nas-backup                       # tonight's snapshot, now (or: launchctl kickstart gui/$(id -u)/local.life-archive-nas-backup)
npm run nas-backup -- verify             # checks the repository and the newest snapshot (below)
npm run nas-backup -- status             # ~/life-archive-data/backups/nas-backup.json, then ~/life-archive-data/transcripts/capture.json
```

**What it protects against.** It covers losing or breaking the Mac's disk, deleting or damaging something in the archive's folder or rituals' (for about a week; Time Machine goes further back), a bad change to the archive found within that time, and anyone else with access to the NAS reading the archive. For the transcripts it goes back to the first night of their snapshots, for good. It does not cover the place itself: a NAS kept beside the Mac goes with it in a fire or theft, and only a Time Machine drive kept elsewhere is left. It is no help if the NAS fails at the same time as the Mac, or if the password is lost along with the Mac. An off-site copy would cover that.

**Verifying.** `npm run nas-backup -- verify` runs `restic check --read-data-subset 5%`: it checks the repository's structure and reads back and decrypts a random 5% of its data, so damage anywhere shows up over a few runs. It then restores the newest snapshot's `core.sqlite`, `calendar.sqlite` and each module's database by its path (`modules/friend-map/archive.sqlite`, `modules/exercise/exercise.sqlite`, `modules/rituals/data/ritual.sqlite3`) into `data/backups/nas/verify/`, runs `pragma integrity_check` on each, deletes them, and checks that each of `nasBackup.folders` is in the snapshot. Then it finds the newest of the transcripts' snapshots and checks that it holds `/transcripts` and `/llm` (each that the archive's folder has). Any error, a database missing from the snapshot or failing its check, a folder missing, or no snapshot of the transcripts, fails it.

**Restoring.** Every restic command needs the repository and the password. On this Mac:

```sh
export RESTIC_REPOSITORY=sftp:<ssh host>:<nasBackup.repository>
export RESTIC_PASSWORD_COMMAND="/usr/bin/security find-generic-password -s life-archive-backup -a life-archive -w"
restic snapshots --tag life-archive                      # every snapshot of the archive's folder, with its id and time
restic snapshots --tag llm-transcripts                   # every night's of the transcripts
```

On another Mac, set only `RESTIC_REPOSITORY` (with an ssh host for the NAS) and restic asks for the password from your password manager.

To look around, or take back a few files: `restic mount ~/mnt/archive-backup` shows every snapshot as a read-only folder (`snapshots/<time>/`, `snapshots/latest/`) until Ctrl-C; it needs macFUSE (`brew install --cask macfuse`). Without it, `restic ls latest` lists a snapshot and `restic restore latest --target ~/Desktop/restored --include /llm/grok-bot` takes back a part of one (snapshots made before the vault moved into iCloud Drive also hold it, as `/Vault`).

To bring back the whole folder, stop the server first (`launchctl bootout gui/$(id -u)/local.life-archive`), and stop the NAS agent the same way while you work. Then restore a snapshot into a new folder, check it, and swap it in:

```sh
restic restore latest --target ~/life-archive-data.restored --exclude /Projects   # or a snapshot's id from restic snapshots; every database lands where it lives
npm run check-data -- ~/life-archive-data.restored               # opens it read-only and checks the people
mv ~/life-archive-data ~/life-archive-data.before-restore && mv ~/life-archive-data.restored ~/life-archive-data
mv ~/life-archive-data.before-restore/Vault ~/life-archive-data/Vault   # the link to the vault in iCloud Drive, which the snapshot leaves out
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/local.life-archive.plist
```

A snapshot from before friend map was a module (its databases at the root by name) needs them put back before the check: `exercise.sqlite` into `modules/exercise/` and `ritual.sqlite3` into `modules/rituals/data/` by hand, then `npm run archive -- migrate friend-map-module --apply --data ~/life-archive-data.restored`, which moves the root `archive.sqlite` into `modules/friend-map/` and the core's rows out of it. Never skip that: without friend map's archive the module would make an empty one at the next start, without exercise's the calendar's workouts empty, and without rituals' store its tabs say rituals is not set up and the next `bin/ritualctl` write refuses.

To bring back only the core's database, `restic restore <id> --target <folder> --include /core.sqlite` and move it into `data/` with the server stopped, after moving the current `core.sqlite`, `-wal` and `-shm` aside. `/calendar.sqlite` comes back the same way; with the core or a module's database alone restored, `npm run archive -- calendar rebuild` brings the calendar's events back in line with them. A module's database comes back from the snapshot's root (`--include /archive.sqlite` for friend map's archive, `/exercise.sqlite`) and goes into its folder (`modules/friend-map/`, `modules/exercise/`), with the server stopped, after moving the current file, `-wal` and `-shm` aside. The restored folder has no `backups/`, which fills again with the next change.

To bring back rituals' store alone, with the server stopped and no logging under way (whatever runs `bin/ritualctl` writes it), restore `/modules/rituals/data/ritual.sqlite3` and move it into `modules/rituals/data/` after moving the current `ritual.sqlite3` (and any `-journal`) aside; rituals' own `data/backups/` (its copy before each write) is not in the snapshot, and fills again with the next write. A snapshot from before friend map was a module holds it at `/ritual.sqlite3`, and one from before rituals became a module holds its folder as `/Projects/rituals/data` too.

To get back a transcript the Mac's `transcripts/` no longer has as it was, find the nights that hold it in the transcripts' snapshots, restore it from one, and read it with `zstd -dc` (see "Every LLM transcript", "Getting one back"):

```sh
restic find --tag llm-transcripts '*<session id>*'      # each night's snapshot that holds it, with its path
restic restore <id> --target ~/Desktop/restored --include /transcripts/claude-code/projects/<project folder>/<session id>.jsonl.zst
zstd -dc ~/Desktop/restored/transcripts/claude-code/projects/<project folder>/<session id>.jsonl.zst > ~/.claude/projects/<project folder>/<session id>.jsonl
```

To bring back the whole of `transcripts/` (stop the NAS agent first, so no pass runs meanwhile), restore `/transcripts` from the newest of them into a new folder and swap it in, as for the archive's folder, then run `npm run nas-backup -- transcripts check`.

### Every LLM transcript

Every transcript the LLM tools on this Mac keep is taken into `data/transcripts/` each night, as its tool wrote it, so that nothing more is lost: Claude Code deletes a session 30 days after it last changed, and firstmate's crews' sessions (most of Claude Code's) were going with them. The archive indexes only some conversations (see events.md's "Conversations with agents, live"); this keeps all of them, as raw material for later (a usage index, the console's views) that nothing reads in the normal course. `server/archive/transcripts.ts` does it, the NAS backup's nightly job (`npm run nas-backup`, at 06:00) runs it just before its snapshot, and the snapshot holds what it took; a second snapshot, of this folder and `llm/` alone, keeps each night's on the NAS for good (see "The NAS copy", "The transcripts, kept for good").

**What it takes** (`TRANSCRIPT_SOURCES`), each source a tool's named folders and files, never its whole home, so the sign-in and secrets files beside them are never taken:

Inside them, a name that is a sign-in or a key is never taken either (`SECRET_NAMES`: `auth.json`, anything with `credentials` in its name, Claude Code's account file `.claude.json` and its backups, `secrets`, `.env` files, keys), nor a symbolic link; each pass counts what it left. Left out on purpose: OpenSuperWhisper's `whisper-models/` (the models' weights, downloaded again from the app), the Claude desktop app's `claude-ssh-remote/` (its remote helper program, no transcripts), Codex's `thread_history_1.sqlite` (made from the rollouts) and `generated_images/`, the T3 databases' hand-made copies, Grok Bot (the archive already logs its chats, under `llm/grok-bot/`) and the Cua Space's sessions (inside its VM).

**How it is kept.** Each file is at its path in its source with `.zst` added, compressed with zstd (level 9, each frame with its checksum), so `zstd -dc` gives back its bytes exactly, and a stored file only ever grows:

- A file new to its tool is compressed whole, through a temporary file flushed to disk and renamed.
- A file its tool added to (Claude Code's sessions and histories) is checked whole against the sha-256 of what is kept, and only what is new is compressed and appended to the stored file as a frame of its own: zstd reads a file of frames as their bytes one after another, so the stored file still gives back the whole.
- A file that no longer begins with what is kept (rewritten, or shorter) is a new version beside it, `<path>.changed-1.zst` (then `-2`, ...: the newest is the highest), and the earlier stays. A database's checked copy (`VACUUM INTO`, then `pragma integrity_check`, as the backups are) is taken only when its file or `-wal` changed, and is a new version each time it did.
- A file its tool deleted stays, marked gone in the index with when it went: Claude Code's after its 30 days, and Codex's `rollout-*.jsonl` when Codex rewrites a quiet one as `rollout-*.jsonl.zst` (in place, with the same modification time), which then is a new file kept beside it; both are kept.
- A file whose size and modification time are as recorded is not read again, so a night costs what changed: about 3 s.

Each source's index, `data/transcripts/<source>.json`, records each file's size, modification time and sha-256, how many versions are kept and the stored bytes of the newest, and when it went if its tool deleted it. It is the record of what has been taken: saved as the pass goes and however it ends, so a pass stopped (a signal, the Mac sleeping) leaves at most a frame the index does not know at the end of a stored file, which the next pass cuts back before it appends. One pass at a time (`data/backups/transcripts/.lock`). A pass refuses to start with under 5 GB free on this Mac's disk, and stops, with what it has taken saved, before the file that would take it under 5 GB (a database counts twice its size, as it is copied before it is stored): the first pass over a big source (OpenSuperWhisper's recordings, several GB) can fill a disk that had the room when it began, and the next pass carries on from the index. One killed outright (`kill -9`, a power cut) is picked up the same way: the files taken since the index was last saved (every 100) are taken again, over what they left.

**OpenSuperWhisper's dictations.** The app keeps every recording and transcript for good (it deletes one only when the captain deletes it, or all of them) but only on this Mac, so the archive takes them too: a `.wav` is taken whole when it is new and, as a recording never changes, not read again; one the app deletes stays, marked gone. `recordings.sqlite` is taken like the other databases, as a checked copy on each night it changed, the earlier copies kept beside it; at about 3 MB (a megabyte or so compressed) a night of use, a year of nightly copies is a few hundred megabytes. A recording the pass finds while the app is still writing it is taken as it is, and what the app adds after is appended, or kept as a version beside if its start changed (as for any file). The audio is zstd'd at the same level 9 as the rest, which saves only about 12 to 14% on speech (measured on made-up speech with microphone noise: level 3 gave 13.5% at 580 MB/s, level 9 14.0% at 213 MB/s, level 19 15.8% at 10 MB/s, a first pass of 6 GB, say, taking about 30 seconds at level 9 and about 10 minutes at level 19, to save under 100 MB more), so such a pass stores about 5.2 GB: more of the NAS's never-forgotten snapshot than of anything else, once. Recordings and transcripts are content in the privacy policy's sense (privacy.md): the pass handles them as bytes, and they are read only as its rule says.

**What each night says.** The log (`~/Library/Logs/LifeArchive/nas-backup.log`) has a line for each source: how many files were new, grown, changed (a version beside), as they were and gone since the last pass, the bytes read, and what it keeps; then a `PROBLEM` line for each file or folder it could not read (`EACCES`, say), which raises a macOS notification. A folder it cannot read marks nothing in it gone, and the snapshot is still made. A pass that fails whole (no room, another running) is an `ERROR` line and a notification, the snapshot is made without it, and the run exits 1. `data/transcripts/capture.json` keeps the last pass, `npm run nas-backup -- status` prints it, and `npm run archive -- storage` ends with a line on it, saying "overdue" after two days without one.

```sh
npm run nas-backup -- transcripts             # a pass now (the night's job runs the same before its snapshot)
npm run nas-backup -- transcripts --dry-run   # what it would take, by size and time; reads and writes nothing
npm run nas-backup -- transcripts check       # reads back every file kept: each version whole, the newest against its index's sha-256, and against its tool's file when that is unchanged
```

**Getting one back.** `zstd -dc` gives a file's bytes; its newest version is the highest `.changed-<n>.zst`, or `<path>.zst` when there is none. One the Mac's copy no longer has comes back from the NAS's transcripts' snapshots first (see "The NAS copy", "Restoring"). A Claude Code session put back in its project's folder resumes (`claude --resume <id>`), as a Codex rollout under `~/.codex/sessions/` does (`codex resume`):

```sh
zstd -dc ~/life-archive-data/transcripts/claude-code/projects/<project folder>/<session id>.jsonl.zst > ~/.claude/projects/<project folder>/<session id>.jsonl
zstd -dc ~/life-archive-data/transcripts/t3code/state.sqlite.changed-3.zst > ~/Desktop/state.sqlite   # a database as it was on a night
```

**Size.** Claude Code's sessions compress to about a quarter (most of what is left is screenshots, which barely compress); Codex's barely do, being mostly zstd already. With agents in daily use it grows by a few GB a month on the Mac's disk, a new copy of each database each night it changed among it. Everything is kept on the Mac; parts of it can move to the NAS when the room matters more.

**Privacy.** The transcripts quote whatever the agents saw: friends' messages they were shown, the captain's screens, secrets a tool printed. They are content (the privacy policy, `docs/privacy.md`): an agent reads one only when the captain asks for something from it, and only for that request. The pass and its check handle them as bytes and hashes, and read none. The originals in the tools' homes are the same content, already readable by anything running as the captain; the archive's copy makes them last, it adds no reader. The NAS's snapshots of them are encrypted on this Mac before they leave it, so the NAS holds only ciphertext; they are read with the backup's password alone, by the same rule. A leaked key is rotated, not deleted from here.
