# The event index

The core's index of events, the calendar, and the folder history module.

## The event index

The archive is growing into a life archive: besides messages, it keeps an **event index** (the `event` table, in the core's own database, `core.sqlite`; `server/archive/events.ts`), one row for each thing that happened, by when (the instant, and its local day), what kind, whether you did it, on which device, which import brought it and which last changed it, and how big its content is, never the content itself. Each row is keyed on its source's own id (`origin`, `native_id`), so importing a source again changes nothing, and one that has grown is brought up to date. Its detail is in a typed table (`detail`, `detail_id`). The index is structure, like counts and dates: anything may read it, SQL queries too. Messages, calls and hangouts are not in it; its source is your conversations with agents (firstmate's, through Claude Code, and your Grok Bot bots'). Your workouts from Polar are the exercise module's, in its own index (see features.md's "Exercise"; the archive's `workout` rows from before it stay until `npm run archive -- migrate friend-map-module --apply`, the friend map step's move, drops them), and your rituals are the rituals module's, read from rituals' own store (see features.md's "Rituals"; the archive's `ritual_checkin`, `ritual_habit`, `ritual_day` and `ritual_workouts` rows from before it, the rituals connector's, stay until `npm run archive -- migrate friend-map-module --apply`, the friend map step's move, drops them). What the Events pages show comes from the **calendar** (next), which the index, the social tables and the modules push into.

### The calendar

The Events page's tables and calendar read one small database of the core's own, `calendar.sqlite` in the archive's folder (`server/calendar/`), rather than asking each part of the archive live, by the captain's call: "it's not even a choice. It's more like the illusion of choice if we want speed and performance." Each part pushes its own rows into it (`server/calendar/push.ts`, through the sink in `sink.ts`), keyed on the module that pushed them, the origin and the source's own id, so a push again changes nothing: friend map's (`friendMap.ts`) every call and every hangout as a **moment** (a card at a time), and two **day summaries** (one row a day with counts): whom you messaged, one row a day for each person with how many messages (the Messages tab's rule: what they sent anywhere, and everything in their one-to-one chat), and how many messages the day had; the index's (`eventIndex.ts`) every agent session, prompt and reply as a moment (the core's own: "we can honestly fold LLM sessions like directly into Life Archive"); the rituals module's every habit done as a moment and a day summary of how each ritual's day went (which habits were done, not done or not reported yet, so the week's Rituals row reads "5/5" from the calendar and never from rituals live), pushed from rituals' store by the module's watch whenever the store changes (`modules/rituals/server/calendar.ts`, `watch.ts`; "Rituals"); and the exercise module's every workout copy as a moment, its `apply` answering the rows and the host pushing them under its name (`modules/exercise/server/calendar.ts`; "Modules"). A row never carries content, and never a name: the people on it are the owning module's person ids, which its owner names at read time through one of the **two hooks** (`owners.ts`: `labelPeople`, the names of the people a row names; `detail`, what a row's drawer adds and where it leads; and, optionally, `hiddenPeople`, whom its own views hide, which the calendar's lists of people leave out until asked), the shape a module declares in its `module.ts` (`events`, `docs/modules.md`), as exercise and rituals do for their rows; until friend map is a module of its own the core answers for it. The days of the summaries are the Events calendar's days, from 06:00 (`src/calendarDay.ts`), as the page counted them before.

**When it is pushed.** After every import, once the archive's transaction has committed (the two files cannot commit as one): the index events the import added or changed, every call again when one came or changed, and the day summaries of the days its messages fell on; after a module's import (the polar connectors', exercise's), once the module's database has committed, the rows its apply changed. After an edit (a changeset touching what friend map's rows read: a hangout added, a call logged or given a length, a name, a merge, a drop, an undo; a tag or an inspiration's caption pushes nothing then, though a tag's `people_version` has the next rules run read the calls and hangouts again, changing nothing): friend map's calls and hangouts again. After the people rules run, the same when the people changed (`people_version`). Either way its day summaries are pushed whole only when who is whom changed since they were last pushed (`friendMapVersion`: every account's person, the captain's own accounts, each one-to-one chat's other person), so a merge reaches whom you messaged each day and a name or a tag never re-counts the messages; most rules runs, one after every live batch, change nothing of that and push nothing. A workout you delete from the Fitness page is taken out of the calendar first, for good, as its rows in the module's database are. A push that fails is said in the log and stops no import.

**Rebuilt from the archive.** The calendar's events are derived: the archive's tables and each module's are the truth (a module's `events.rows`, exercise's every workout copy), and they can be built again, whole, at any time, which `modules/friend-map/server/calendar.test.ts` proves gives back what the pushes made, row for row, after imports, edits, a merge and its undo (friend map's rows, from its `calendarRows.ts` and `calendarPush.ts`, beside the core's own index). The server builds it once, when it is new (the first start after the calendar came, or a testing folder; the trail of content reads the archive held, below, is copied into it first), and says so in its log. A module switched off is left alone: its rows stay as they were, out of sight without its tabs, neither the check's drift nor the rebuild's to change, and its pushes go on from there when it is on again.

**After an edit** in a cell or a row's drawer (console.md's "Editing"; modules.md's "Editing a table"), the row's owner pushes it at once: friend map after the changeset commits, exercise its activity's copies, rituals its rows whole. A change to an imported row is the captain's correction kept beside it, which every read of the owner's store takes over it, so the corrected row is both what was pushed and what a rebuild makes: `modules/exercise/server/workoutEdits.test.ts` and friend map's calendar test hold a rebuild to changing nothing after corrections, an import of the same copies again, and undos, and `modules/rituals/server/edits.test.ts` the same of rituals' pushes after ritualctl's writes.

```sh
npm run archive -- calendar             # how many rows of each kind each module has, and when it was last built whole
npm run archive -- calendar check       # what a rebuild would change: rows missing, differing or extra (exit 1 when any)
npm run archive -- calendar rebuild     # build it again, whole, from the archive; nothing of the archive changes
```

A rebuild holds the calendar for as long as it takes, from its read of the archive to its last write, so what the server pushes meanwhile waits and lands on top of it rather than being undone. The server's content reads wait too, as the trail is in the same file. Each write waits ten seconds at most, and while it waits the whole server is held: its one thread answers nothing. A write still blocked after that fails, a content read with it. A failed push is said in the log and the import stands, but the calendar has lost it: calls and hangouts come back with their next push, which replaces them whole, while a day's summaries or an index event come back only if a later import touches them again, and otherwise only with a rebuild (`calendar check` shows them). So on a large archive a rebuild is best run with the server stopped.

**The trail of content reads** (`content_read`, "The message archive") lives in the calendar's file too, since what is read may live in any module: the archive's own table, which held it before, was copied into it once, and the friend map step's move (`npm run archive -- migrate friend-map-module`) dropped it from the archive, after copying any read not yet in the calendar. It is not derived: a rebuild leaves it alone, nothing can build it again, and reads made since it moved are only in this file, so the NAS backup sends a checked copy each night and a lost `calendar.sqlite` is restored from there, not rebuilt. The 48-hour backups taken before an edit are of `archive.sqlite` alone.

### Conversations with agents, live

Each agent is a connector, a small plug-in (`server/connectors/conversations.ts`'s `ConversationSource`: where its conversations are, how to copy one, how a copy becomes sessions and turns), and everything else is shared, so another agent (Codex, the Grok CLI) is one more plug-in:

- **Copies.** The agents' apps keep their conversations only for a while (Claude Code deletes a session file 30 days after it last changed; Grok Bot keeps a bot's last 200 entries), so the archive keeps its own copy of each, in `data/llm/<origin>/` in the archive's own layout for it, and reads only the copy (`server/connectors/sessionCopies.ts`). These are the conversations it indexes; every other transcript (firstmate's crews, subagents, other projects, Codex and the other tools) is kept apart, unread, in `data/transcripts/` (see data.md's "Every LLM transcript"). A copy only ever grows: it is first written whole (a temporary file flushed to disk and renamed) and then only appended to, flushed to disk; nothing in it is ever written over or taken out, and a conversation the app has deleted keeps its copy, read as before.
- **Live, in the archive's server.** The server runs each agent's connector as it runs the live bridges (`server/connectors/sync.ts`, one process on an archive at a time): it watches the app's folders (macOS's file events), and about 2 s after a change settles (at most 10 s while they keep changing) it copies what is new and reads the conversations that changed. It reads every conversation again when it starts and every hour, for anything missed or changed while it was down. Each pass's events are written in one transaction with its **bookmarks** (each copy's size when last read, in the connector's cursor), so a crash leaves nothing half done: the copies are ahead of the bookmarks at most, and the next pass reads them again, which changes nothing. A pass of one origin at a time, in any process: `npm run archive -- import <connector>` runs the same pass by hand (reading every copy again) and waits for the server's, and its bookmarks are kept the same way (the lock is `data/llm/<origin>/.importing`, naming the process holding it; one left by a process that died is taken over).
- **Never guessed.** A conversation in a shape the plug-in does not know (an app's undocumented format that changed) is not read: its bookmark stays, the import's tallies and `connectors` (`live: error (... not read: ...)`) say why, and its copy keeps what can be kept.
- **The index.** Each session is an `llm_session` event (how it was run or which surface, from its first entry to its last, the bytes of its copy, the folder it ran in or the bot it is with, and the model most of its replies came from), each prompt you wrote an `llm_prompt`, and each reply an `llm_reply`, with what started its turn (its subkind). A prompt or reply is kept as its length in characters and where its lines are in the copy (`llm_turn`: its first line, byte offset and length), never its text. A turn a continued session repeats stays with the session that brought it first. Its imports bring no people, so the rules do not run after them.

**Your conversations with firstmate** (`llm-sessions`, origin `claude-code`). Claude Code keeps each session as a file of JSON lines, `~/.claude/projects/<project folder>/<session id>.jsonl`, the folder named by the project's path with every character but a letter or digit made `-`. Each is copied byte for byte, to its last whole line (a line still being written is left for the next pass), into `data/llm/claude-code/<project folder>/<session id>.jsonl`: every session file at the top of the projects' folders, whether the index keeps that session or leaves it out. Claude Code only ever adds to a session file; one that changed any other way (shorter, or no longer beginning with the copy: each pass checks the copy's last 64 KB, the hourly pass all of it) never touches the copy, which stays what the index reads, and is mirrored beside it instead, into `<session id>.jsonl.changed-1` (or `-2`, ...: the first it extends, or a new one), and counted. Nothing reads those. The connector reads only:

- the projects in `projects` in `data/connectors/llm-sessions.json` (`llmSessions.projects` in the archive's settings unless said; with neither it stops and says so), and of each only the session files at the top of its folder: never the folders beside them (a session's subagents, its tools' output), nor any other project's (firstmate's workers and scouts, worktrees);
- sessions someone was at. Every entry says how its session was run (`entrypoint`): `cli` (a terminal) or `claude-desktop` when someone was at it, `sdk-cli` (print mode, `claude -p`) or `sdk-ts` and `sdk-py` (the Agent SDK) when it ran headless, as firstmate's own supervision runs do. A headless session is left out and counted, and so are a session run in another folder that makes the same folder name, and one where you wrote nothing.

Each prompt you wrote is a user entry Claude Code marks `origin.kind` `human` (what you typed, not a tool's result, a meta entry or a background task's notice); each reply is the model's entries after what started its turn (your prompt, or a notice Claude Code passed on, such as a crewmate's task notification, which is its subkind), when they hold any text, with their model, how many tools they used and the prompt they answer. Claude Code's own stand-in replies (the model `<synthetic>`) are left out.

**Your Grok Bot bots** (`grok-bot`, origin `grok-bot`). The Grok Bot desktop app keeps each bot's chat in its cache, `~/Library/Application Support/Grok Bot/sand-client-persistence/`, as a `.blob` file of JSON named by its key in base32 (`sand.client.slice.account.<account>.transcript.replicas.<bot id>`): its last 200 entries, the file written whole on each change. The archive keeps each bot's chat as a log, `data/llm/grok-bot/<bot id>.jsonl`, one entry a line as the app had it: each entry it has not seen is appended, and an entry the app changed (a reply that was still streaming) is appended again, its last line the one read; an entry the app drops stays. Only the chats and the bots' names (the app's roster) are read: never a draft, the settings, or the secrets and sign-in files beside the folder. A bot's chat is three kinds of session, its surfaces (`server/connectors/grok-bot/entries.ts` has the detail):

- the chat window (subkind `chat`): your messages are prompts; another agent's message starts a turn of its own (`agent`); the bot's words, a widget's question, a file or an approval are its reply;
- a call (`call`, one for each finished call): its transcript, your words a prompt (the transcriber's streamed partials of one utterance joined, as rituals' voice calls do) and the bot's a reply;
- backstage on a call (`backstage`, one for each call's channel): the call agent passing your words to the bot, and the bot's answers there.

A reply whose start dropped out of the cache before the archive saw it answers `unseen`; the bot's opening words on a call, `call-start`. Your attachments and the app's own notes (its `event`s, and its `notice`s, a line such as that a background task was stopped, set among a reply's entries) are no turn: they stay in the copy, and a reply a notice sits in stays one reply. An entry of a kind the archive does not know stops its chat from being read (its entries are still copied) until `entries.ts` learns it, and the connector shows `error` until then.

```sh
npm run archive -- enable llm-sessions                             # and enable grok-bot: the server follows each from then on
npm run archive -- connectors                                      # live: connected (watching 1 of 1 folder), or why not
npm run archive -- import llm-sessions                             # the same pass by hand: copies, then reads every copy again
npm run archive -- events                                          # how many events of each kind, from the first day to the last
npm run archive -- events --day 2026-10-09 --kind llm_prompt       # a local day's events in time order: number, time, kind, size, detail
LIFE_ARCHIVE_READER=claude-code npm run archive -- event-content <event> --why "<the captain's words>"
LIFE_ARCHIVE_READER=claude-code npm run archive -- event-content --latest grok-bot --last 20 --why "<the captain's words>"
```

**Their text** is content and stays in the copies: the index's `llm_session.file` is the archive's copy, named relative to the archive's folder (`llm/claude-code/...`, `llm/grok-bot/...`), and never the app's own file (a session imported before the copies named Claude Code's file by its full path, and moves to its copy, its places in it unchanged, at the next pass). `event-content <event>` reads a prompt's or a reply's text, or every prompt and reply of a session, from the copy (`server/archive/llmContent.ts`, each origin its own way: Claude Code's from the lines where the index says, checking that the line there is the entry the index names; Grok Bot's by reading the bot's chat again and finding the turn), checking that its text is as long as the index says: a copy that is not is refused, saying to import again. `--latest <origin>` reads the session of an agent that went on latest instead (or of one way it ran, `grok-bot/chat`, `grok-bot/call`, `claude-code/cli`), and `--last <n>` only its last n turns, so "have a look at what Grok said" is one logged read. Every read is kept in the trail of content reads, and it takes `--why`, `--redacted` (every text as its length) and `--json` as `timeline` does.

### The LLM warehouse

Every LLM session on this Mac is in the index too, not only the conversations the connectors above bring: every Claude Code account's (`~/.claude/projects`, each profile's `<name>/projects` in `CLAUDE_PROFILES_DIR` when `.env.local` names it, subagents' files included), Codex's (`~/.codex/sessions`, `archived_sessions`), the Grok CLI's (`~/.grok/sessions`) and Pi's (`~/.pi/agent/sessions`), firstmate's workers, the review pipeline and the programs' own calls among them, and a session its tool has deleted from the archive's copy of it (`transcripts/`, data.md's "Every LLM transcript"). The captain: "I think it would be ideal for us to ... have analytics over our entire transcriptions ... how many of our prompts came from a phone. How many came from, like, 1st mate delegated". The code is `server/llm/`.

- **The index.** Each session is an `llm_session` event, each prompt an `llm_prompt` and each reply an `llm_reply`, by its tool's origin (`claude-code`, `codex`, `grok-cli`, `pi`; read by `claude.ts`, `codex.ts`, `grok.ts`, `pi.ts`), with what the tools record of them: tokens (`input_tokens`, which counts the cached, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`), the cost the tool says (`cost_usd`), pictures and tool calls, and `facts`, what the file says of a session (its account, Codex's app and source, a subagent's parent) or of a prompt (how it came, and what its text is, `markers.ts`: a tool's notice or hook feedback, a slash command, and, where an orchestrator's provenance is configured (below), its own shapes, FirstMate's launch brief, its doorbells and wake-ups; a tool's own lines, an interruption or Codex's context, are no prompt). A prompt's text is read only for that and for its length, never kept. A session the connectors keep (firstmate's own in `llm-sessions`' projects, Grok Bot's) stays theirs: the warehouse adds its measures and facts, and tags it. The warehouse's sessions stay out of the calendar (the agents' row shows the connectors' conversations, as before); the Events page's tables below show them.
- **The tags** (`llm_tag`): each row is on a session or a prompt (`target`), in a family, with its value, the rule that gave it (or `hand`) and whether it is a guess; `chosen` marks the one value of each family the tables read: the captain's own, else a fact's over a guess's, else the earliest rule's. The families: on a session, `tool` (claude, claude-<profile> for each Claude Code profile in `CLAUDE_PROFILES_DIR`, codex, grok, pi, g), `app` (t3, claude-desktop, codex-desktop, vscode, chrome, terminal, g-app, program), `session` (own, worker, decision, review-pipeline, helper, app-internal, and with FirstMate's provenance firstmate-main and secondmate), `task` (a worker's task, from the orchestrator's own records alone: FirstMate's thread's `state/<task>.meta`, else the launch brief written nearest the session's start for its project; never from a prompt's text) and `project`; on a prompt, `who` (human, worker, agent, system, and with FirstMate's firstmate), `device` (desktop, phone, tablet, terminal, unknown; a person's prompts only) and `channel` (typed, voice, command, decision-reply, wake-up, hook, notification, agent-message, continuation, and with FirstMate's initial-instructions, inbox-note and steer). `npm run llm -- rules` lists the rules (`rules.ts`); they read the index's rows and facts, T3's own records (its database, `T3_CODE_STATE` in `.env.local`, none unless named; read-only: which thread each session runs in, who sent each message and from which client, and the device T3 stamps on a message once it does; a message without a stamp is from T3's mobile app when T3 says so, else a desktop by guess) and an agent orchestrator's, where the installation configures one, never a file, so a better rule retags the whole history at once, and running them again changes nothing.
- **An orchestrator's provenance** (`provenance.ts`) is optional: the narrow questions the rules ask an orchestrator that runs agents' sessions (what its markers say, which sessions are its workers' and its own, which senders and folders it knows), answered from its records, read fresh at each retag, and its prompt shapes, read at the import. The one there is is FirstMate's (`firstmate.ts`), configured by `FIRSTMATE_HOME` in `.env.local`: its tasks' folders and launch briefs, its live tasks' T3 threads, its own thread and its secondmates' homes. Without one, the rules give only the tools' and T3's tags: a T3 crew's thread is a worker by guess, steered by an agent, and a marker kept from before says nothing. A rule that needs more of the text than the facts hold needs the files read again (`import --again`).
- **When.** Each night, by the NAS backup's job (`npm run nas-backup`), after it takes the transcripts and before its snapshot; or by hand. A pass reads only the files that changed since the last (`llm_file`, its bookmarks, written with each file's rows), so the first, of every session there is, can be cut short and goes on where it stopped: thousands of files take seconds.
- **The tables.** Events, Tables lists **Prompts** (every prompt, its who, device, how, and its session's tool, app, kind, project and task; the chart counts them over time split by any of those, as phone against desktop for the captain's, or his against firstmate's), **Agent sessions** (each session with its prompts, replies, tokens and cost) and **LLM tags** (every tag, with its rule, strength and whether it was chosen), all read from the core's database (`server/viewer/llmWarehouseTabs.ts`, `server/llm/views.ts`).

```sh
npm run llm -- import                       # the files that changed, then retag (--again: every file)
npm run llm -- retag                        # every rule over the whole history, after a rule changed
npm run llm -- tags                         # how many sessions and prompts have each chosen tag, and how many are guesses
npm run llm -- summary --by device --grain week   # prompts over time by a family (who unless said)
npm run llm -- tag <event> who human --why "<the captain's words>"   # his own tag on a session or prompt; untag <event> who takes it off
```

A trial on a core database of its own reads the real tools' files and only reads the archive's folder: `npm run llm -- import --data ~/life-archive-data --core /tmp/trial/core.sqlite` (it reads the connectors' sessions too, since that core has none of them).

### Rituals' habits and days, from the rituals module

The rituals connector went with the rituals module (see features.md's "Rituals"): the module reads rituals' store itself and pushes each habit done and each day's summary into the calendar in its own name (`modules/rituals/server/calendar.ts`), the same rows keyed the same as the connector's were (`habit/<rituals' id>`, `tick/<day>/<habit>` for a habit a day ticks done with no doing of it, `day/<day>`), so the Events pages read what they read before. The check-ins and the days of workouts it also indexed are no longer anyone's to index: nothing on the calendar drew them, and the Fitness page reads the workouts logged in Rituals from the store through the module's service. The archive's `ritual_checkin`, `ritual_habit`, `ritual_day` and `ritual_workouts` events from before, their detail rows, the connector's runs and the copies of each day's workouts in `platform-exports/rituals/workouts/` stay as they were, read by nothing, until `npm run archive -- migrate friend-map-module --apply` (the friend map step's move) overwrites the rows for good (the copies are removed by hand).

The Ritual days table (`modules/rituals/server/daysTab.ts`) reads the day summaries, one row a day with each habit's standing and how many of the day's items were done; it is where a habit's day is set done or not (`modules/rituals/server/edits.ts`, through ritualctl), as a habit done's own row is from its drawer on the Calendar.

### Workouts from Polar

Runs recorded through the Polar Flow app (with a chest strap, say) come in from two sources, both origin `polar`, each a connector of the exercise module (`modules/exercise/connectors/`, run by the core's host as its own connectors are, each import applied to the module's own database and the rows it changed pushed into the calendar; see features.md's "Exercise"):

- **`polar`, live**, through Polar's official API (AccessLink v3, `modules/exercise/connectors/polar/`), as the captain's own registered client. After one login it needs nothing: the archive's server asks Polar when it starts and every 3 hours (`pollEveryHours` in its settings), under the live connectors' lock, for the exercises uploaded to Flow in the last 30 days (all AccessLink gives, and only those uploaded after the login), and keeps each new one as Polar gave it, written once and never changed: `data/platform-exports/polar/accesslink/<exercise id>.json` (with its samples, zones and route) and `<exercise id>.fit` (tried again each pass until Polar has it). Every good pass ends in a checkpoint, a pass that found nothing new too, so `connectors`' last good run is the last time Polar answered, not the last time it had something new. Polar refusing the token (401) is "reconnect needed": `connectors` says `live: logged-out (reconnect needed ...)`, and the server asks Polar nothing more until the Keychain holds another token (a login again), looking each minute. `npm run archive -- import polar` is the same pass by hand.
- **`polar-export`**, Polar's account data export (account.polar.com, Download your data), filed and unpacked in `data/platform-exports/polar/<export date>/` as every export is: each `training-session_*.json` read where it is (`modules/exercise/connectors/polar-export/session.ts`), never copied or changed (but removed, with its entry in the export's zip, when the captain deletes its activity: see features.md's "Exercise"). It reaches as far back as the account does, which the API never will.

Each copy is one `workout` event, as the connector writes it, and one row of the module's index (`workout` in `modules/exercise/exercise.sqlite`, `modules/exercise/server/workoutIndex.ts`): from its start to its end, its sport family (run, walk, ride, swim, other) as its subkind, the bytes of its copy as its size, and what the copy holds, never a heart rate or a coordinate: the sport in the source's word, how far, what recorded it ("Polar Flow app", or a watch's name), which sample streams it has with how many samples and how often (heart rate, RR, GPS, speed, distance, cadence, altitude, power, temperature), and where the copy is. The API's copy is keyed on Polar's exercise id, the export's on `export/<its id>` (the export numbers exercises its own way). The copies are content: the route says where he ran from, and the samples his heart rate.

**One activity, many copies** (`modules/exercise/server/workouts.ts`). Polar can copy each run to Strava and Apple Health, and the API and the export each have it, so one run can be several copies. Every copy is kept as its source gave it; which are one activity, and which to show, is worked out over the index each time, never stored, and source-blind, so Strava's export or Garmin's join by giving their copies the same shape. Two copies are one activity when they are of the same sport family, start within two minutes of each other and share at least 80% of the shorter; they join in chains, so any number of sources' copies of one run are one. The copy shown is the one with the most detail, by a fixed order where the first difference decides: heart rate the captain trusts; heart rate sample by sample over a summary; RR intervals; a GPS route; more of the other streams; heart rate sampled more often, then more samples; a hardware maker's own copy (Polar's, Garmin's) over an aggregator's (Strava's) over one transcribed by hand; then the copy the index had first. A run only one source has is an activity of one copy. The viewer lists each activity once, in the Workouts table in Events' Tables (see console.md's "The viewer"), matched the same way, and Exercise shows each with its route, splits and trusted heart rate (see features.md's "Exercise").

**Whose heart rate is trusted** is the captain's word, in each source's settings, since Polar never says which sensor a heart rate came from (the Flow app reports itself, whatever it paired): `data/connectors/polar.json`'s `trustedHeartRate`, a list of the recorders whose heart rate he trusts, each with the sensor behind it for the page, `[{"device": "Polar Flow app", "sensor": "Polar H10"}]`, written once when only a chest strap is paired with the app. A watch names itself, so its heart rate stays untrusted. `polar.json` holds no secret:

```json
{ "enabled": true, "memberId": "life-archive-1a2b3c4d", "trustedHeartRate": [{ "device": "Polar Flow app", "sensor": "Polar H10" }], "pollEveryHours": 3 }
```

**The secrets** are in the login Keychain alone, service `life-archive-polar`: `client`, the API client's id and secret, and `token`, the access token and his Polar user id (`modules/exercise/connectors/polar/secrets.ts`), stored through `security`'s standard input, never a process's argument, a file or a log.

**Once, to connect** (only the captain can; about ten minutes):

## Folder history

The archive can keep a private git history of folders it does not own, such as a shared Google Drive folder. Drive keeps only about 100 versions or 30 days of each file and never says what changed across files at once, so the archive's server records the folder into a git repository of its own as it changes. It is a module, `modules/folder-history/` (its README): the watcher is the module's work while the server runs (`modules/folder-history/server/folderHistory.ts`), and `history` its command of `npm run archive` (`server/commands.ts`); switched off (`"modules": {"folder-history": false}`), nothing is recorded. Code kept in such a folder belongs in a repository of its own; this is the data's history.

- **Which folders.** `data/connectors/folder-history.json` names them, each with a name and a path: `{"folders": [{"name": "shared-notes", "path": "~/Library/CloudStorage/GoogleDrive-you@example.com/My Drive/Shared notes"}]}`. The path may be Drive's shortcut (a link into `.shortcut-targets-by-id/`); it is followed each time, so a shortcut that moves is followed. The server reads the settings when it starts.
- **Where.** Each history is `data/history/<name>/`, a bare git repository in the archive's folder, so the NAS's nightly snapshot keeps it (see data.md's "The NAS copy"). It has **no remote, ever**: one that has a remote is refused (`not kept: ... has a remote`) until the remote is removed, and nothing here pushes. The folder is named as its work tree on each command and never in the repository's settings, so a git command run there by hand cannot write into the folder either.
- **Never writes into the folder.** It only lists the folder and lets git read its files. While the folder is not there (Drive not running, signed out) nothing is recorded, not even as deleted.
- **When.** When the server starts, about 3 s after a change in the folder settles (macOS's file events; at most 30 s while changes keep coming), and every hour for anything missed. Each commit is the folder's files exactly as they are: added, changed and deleted, listed in its message (`3 files: 1 added, 1 changed, 1 deleted`, then a line per file), by "life-archive folder history", since Drive does not say who changed a file. Left out: hidden files and folders (a name starting with `.`: Drive's `.tmp.drivedownload` and `.tmp.driveupload`, `.DS_Store`, a nested `.git`), Office's `~$` owner files, `Icon` files and `*.tmp`. The folder's own `.gitignore` files are not the history's: every other file is kept.
- **Drive's conflict copies.** When two edits collide, Drive keeps both, the second as a numbered copy (`todo (1).md` beside `todo.md`). Each one is said in the server's log (`[history] shared-notes: 1 Drive conflict copy: todo (1).md (beside todo.md)`), and in `history`, to be resolved by hand in the folder. The history keeps it as it keeps any file, and never touches it.

```sh
npm run archive -- history                    # each folder: its history's commits, what is not in it yet, and its conflict copies
npm run archive -- history shared-notes         # its last 20 commits, each with the files it added, changed or deleted (never their content)
npm run archive -- history shared-notes --last 100
git --git-dir ~/life-archive-data/history/shared-notes log --stat   # or any other git command that reads; git --git-dir ~/life-archive-data/history/shared-notes show <commit>:todo.md for a file as it was
```

To get a file back as it was, `git --git-dir ~/life-archive-data/history/shared-notes show <commit>:<path> > ~/Desktop/<file>` and copy it into the folder yourself.
