# Modules

The life archive is a core and modules, by the captain's word: "you just have a singular server that takes in stuff and then all of these modules become like plugins to the core", so that in time "they can pick rituals as a module, exercise as a module, friend map as a module". One repository holds the core and the modules; a module is switched on and off in the settings; every module runs inside a life archive, never on its own. Health is the first module (`modules/health/`), exercise the second (`modules/exercise/`), the first with a database of its own, connectors, rows in the calendar, a table on the Events page and a command ("One database per module, each sending its events to core's calendar, so removing a module is clean and nobody carries an empty messages database"), journal the third (`modules/journal/`), the first with a job of its own outside the server, a launchd agent its command installs, and with no page half until its Journal page came on 9 November 2026 ("Journal is a module; it uses Obsidian, which is like fine"), and rituals the fourth (`modules/rituals/`), rituals' own code brought in from its repository, the first whose store is its own code's rather than one the core opens, read in-process, its rows kept in the calendar by a watch while the server runs, and friend map the fifth (`modules/friend-map/`, its README), the social layer: the message archive, the twelve chat connectors and their jobs, people, friend-map's contract and page, and the Messages, Calls, Hangouts and People tables, the first a part of the core this large and the first to mount paths outside its own place and serve a page, and shopping the sixth (`modules/shopping/`, its README), the Shopping page, a part of the core until 8 November 2026, the first whose `work` runs through a service of its own (its morning pulls, through `Shopping`), and the folder history the seventh (`modules/folder-history/`, its README), the server's watchers of folders the archive does not own and their `history` command, taken out of the core whole, and the inspirations the eighth (`modules/inspirations/`, its README), the core's until 8 November 2026, the first to take its rows over from the core's own database (`takeOverFrom`) and to copy its kept files into its own folder as it does; this file says what is built.

## The shape

- **The core** is the rest of the repository: the server's door and lifecycle (`server/main.ts`, `server/serverLayer.ts`), the console shell and its registry (`viewer/console/`), the Events pages, the connectors' host, the core's own database (`core.sqlite`: the agents' sessions and the event index, and the inspirations' old copy, read by nothing since their module took them over), the calendar and the trail of content reads, the backups, the privacy guard, the settings, and the SDK. Nothing in it names a person.
- **A module** is a folder `modules/<id>/` whose `package.json` says `"lifeArchive": true`; the folder's name is its id. It has two entry files the core imports, `module.ts` (its server half) and, when it has a page, `viewer.tsx` (its page half; journal has none, since nothing of it is shown in the console), and beside them whatever it needs: health has `wire.ts` (the addresses and shapes both halves share), `server/` (its route, its judging, its import), `viewer/` (its views), `fixtures/` (its made-up data), `cli.ts` (`npm run health`) and a README; exercise has the same and `connectors/` (its two Polar connectors), its database's schema and its index in `server/`, and `cli.ts` (`npm run exercise`); journal has `jobs/voice-journal/` (its first job: one pass of the voice journals' transcription, Voice Memos' recordings, the ledger, the launchd agent and its command) and `jobs/grok-calls/` (Grok Bot's finished calls copied into the journal, once rituals'), `src/` (the journal's day, which both file by), `server/` (its privacy lines), `fixtures/`, `cli.ts` (`npm run journal`, which hands each run to a job's command) and a README; rituals has rituals' own `bin/`, `src/`, `tests/` and `HANDOFF.md` beside its halves, `server/` (the store read through rituals' view, its rows, its watch, its service, its routes, its tab), `viewer/`, `fixtures/`, `cli.ts` (`npm run rituals`), a README and an `AGENTS.md` of its own (rituals' logging rules); friend map has `server/`, `connectors/`, `jobs/`, `fixtures/`, `testing/` (what its tests open an archive with), `viewer/`, and `page/`, friend-map's page (once friend-map-frontend's, now this project's own, changed here as any other code), and no `cli.ts`: its commands are `npm run archive`'s, handed to it; shopping has `wire.ts`, `server/` (its route, its service and morning pulls, the storefronts' readers and its suppliers), `viewer/` (its view, its arithmetic and its own stylesheet) and a README, and no database, fixtures or `cli.ts`; the folder history has `server/` (the watcher and its command) and no database, route or page, its one command `npm run archive`'s too; the inspirations have `wire.ts`, `demo.ts` (the static demo's live reads), `server/` (their database and take-over, store, kept files, routes, worker, previews, AI tags and commands, which `npm run archive` hands to it), `viewer/` (its view, its tabs and its own stylesheet), `fixtures/`, `testing/` and a README.
- **The SDK** is what a module imports of the core, and all it imports: `sdk/server.ts` for its server half (how a module declares itself, the pieces a route is made of, the errors it answers, the services it may yield or offer, the calendar's shapes, what the core's jobs share for a job of its own (the lock, a launchd agent and the launcher Full Disk Access is given to), the notifier (`Notifier`: FirstMate's inbox where the installation has one, else this Mac's notifications), the AI service (`AiService`: Codex where a model is named, else none) and the transcribers, a few helpers), `sdk/viewer.ts` for its page half (how it declares its aspects and views, the console's addresses and blocks), `sdk/wire.ts` for what both halves share (the addresses, the archive's clock and the words for a habit done), `sdk/contract.ts` for friend-map's contract (`src/archive.ts`), which friend map's page imports through it, `sdk/connector.ts` for a connector of its own (the events it writes, and `runConnector`, the connector's side of the host), `sdk/command.ts` first in a command (the pinned Node and the settings), and `sdk/testing.ts` in its tests alone (a life archive on a testing folder with the module loaded). A module finds the SDK by its place, `../../sdk/server.ts`; `sdk/sdk.test.ts` holds every module's imports to the SDK and its own files, and holds the core to importing no module by name.
- **No packages of its own.** A module uses the root `package.json`'s packages, and its own `package.json` is only its manifest. Rituals was the first to need packages the core did not have (`@effect/platform-node` and `@effect/sql-sqlite-node`, pinned at the root's `effect` version, and `@effect/platform-node-shared`, an exact pin of platform-node's own dependency, since left to its range, `^4.0.5`, it resolves to 4.1.2, whose peer is `effect ^4.1.2`, a version the root does not have): they went into the root `package.json` rather than bringing npm workspaces in, since a module in this repository shares its lockfile anyway; `"workspaces": ["modules/*"]` is still for a private module cloned in with packages of its own, which has to settle what they do to the tracked `package-lock.json`.

## What a module declares

`module.ts` exports `defineModule({...})` (`sdk/server.ts`'s `ModuleDefinition`). What a route, the services, the events and the work are given (`ModuleContext`, the archive's folder) grows to the module's open database (`ModuleStore`, with `db`) when it declares one, and always carries `ModuleLive`: its `calendar` (`push`, rows added or changed; `replace`, which makes its rows these and no others, or, given a scope, those of some kinds or days; and `forget`, which takes rows out for good, below), `pausingLive`, which runs a change with its live connectors stopped and starts them again (exercise's delete), `host` (the connectors' host as a module may ask it: their statuses and manifests, the platforms that can send and the sender for one; friend map's contract and sends) and `contentLog` (`record`, a content read kept in the trail; friend map's content routes). Before the archive is open each throws why.

| Field | What |
|---|---|
| `id`, `sdk` | its id, which must be its folder's name, and the SDK major it was written for (`SDK_VERSION`, 1); another major is refused with a plain message |
| `database?` | its own SQLite database (`ModuleDatabase`): the file's name, kept in `modules/<id>/` of the archive's folder (`exercise.sqlite`, friend map's `archive.sqlite`), its migrations (one SQL string a step, run by the core as the archive's are, `user_version` counting them; a `meta` table is the core's, there before them, `getMeta` the module's to read), and `takeOver?`, for a module that was a part of the core: run once, when the database is new beside an archive, with the archive attached read-only as `archive` (archive.sqlite, or the database its `takeOverFrom` names: the inspirations' `core.sqlite`) and given the archive's folder, to copy in the rows (and files) the archive held for it, in one transaction a throw undoes, the module broken until the next open tries again (`meta`'s `taken_over` then says the day, or `nothing` with no archive there; a `takeOverFrom` database the friend map step's move has not made yet (no `core.sqlite` while `archive.sqlite` is still at the folder's root, or a `core.sqlite.partial` beside it) leaves the module broken, its database written by nothing, until `npm run archive -- migrate friend-map-module --apply` has run). The core opens it in WAL mode before the archive and closes it after (`server/modules/store.ts`); a module whose database cannot be opened or migrated is broken. `npm run archive -- backup` keeps a checked copy of it beside the core's, and the NAS backup sends one each night, at the snapshot's root by its file name. A database with a runner of its own (friend map's, whose migrations were the archive's) declares `open(file, folder)` in place of migrations, which it leaves empty, and `version`, the schema version its open brings it to, so `npm run archive -- migrate` knows when it is behind; and any of `reads(file)`, the read-only connection the viewer's tables read it on (friend map's refuses content as its SQL runner does), `dryRun(file, folder, platform)`, the copy in memory an import's dry run is applied to (friend map's: the platform's records alone, no content), and `migrated(db)`, the lines `migrate` says after it (what friend map's migrations made of Met and Lives) |

The host finds them with its own and runs them the same way (its process, spool and live lock; `npm run archive -- enable <id>`, `import <id>`, `connectors`, the Sources tab), and keeps their runs and cursors in the module's database (`source` and `connector_state`, `CONNECTOR_TABLES` among its migrations), never in the archive |
| `routes?` | one route (`server/jsonApi.ts`'s `Route`: an Effect program per request, its errors in its type), mounted at `/life-archive/api/m/<id>` and under it, and at each of its `mounts`; it yields the SDK's services it reads (`RunsByHand`, `Exercise`, `RitualWorkouts`, `RitualHabits`), optionally with `Effect.serviceOption` |
| `services?` | the services it offers the core and the other modules, as an Effect Layer: each a service the SDK names (`RunsByHand`, `Exercise`, `RitualWorkouts`, `RitualHabits`), so the asker's type says what it asks for and `Effect.serviceOption` lives without it |
| `events?` | for the rows pushed in its name into the calendar (`ModuleEvents`): the calendar's two hooks (`server/calendar/owners.ts`; events.md's "The calendar"), `labelPeople(ids)`, the names of the people its rows name, by its own ids, and `detail(kind, origin, nativeId)`, what a row's drawer adds (fields, the other tabs narrowed to it, and the id the content routes take when content stands behind it), which the viewer asks with the calendar's rows, never the module's tables; optionally `hiddenPeople(ids)`, which of its people its own views hide unless asked (friend map's: archived, or with a tag its Hide starts on), whom the Events calendar's lists of people leave out until its switch shows them; and `rows()`, every row the module would push now, for `calendar rebuild` and `calendar check` |
| `work?` | its own work while the server runs, an Effect run in a fiber of the server's scope and interrupted as the server stops (`server/modules/loader.ts`'s `moduleWork`, built after the modules' services, so it may yield the services its own `services` offer): rituals' watch on its store (`modules/rituals/server/watch.ts`), which ritualctl writes outside the server, pushing its rows through `calendar.replace` as the store changes; shopping's morning pulls, through its `Shopping` service (`modules/shopping/server/pull.ts`); the folder history's watchers of its folders (`modules/folder-history/server/folderHistory.ts`), a record begun finished as it is interrupted |

The Events page's Tables is the one place a table is shown and edited: a module's page draws none of its own, and the SDK gives it nothing to draw one with |
| `edits?` | its editors for its tables (`server/edits/editor.ts`'s `TableEditor`, one for each table of its that declares fields to edit; "Editing a table" below): friend map's Calls, Hangouts, People and Tags, exercise's Workouts, rituals' Ritual days and Rituals |

One that throws tells its page nothing, and the log says why |

**The calendar** (`server/calendar/`, events.md's "The calendar") is the core's: one small database the Events page's tables and calendar read, which each part pushes its rows into (moments, and a day's summaries), keyed on the module that pushed them. A module's rows go in under its own name: after each of its connectors' imports the host pushes what its `apply` answered; a module whose store is written outside the server pushes them itself through the calendar the core lends it (`ModuleCalendar`'s `replace`: its rows made these and no others, in one transaction; rituals' watch); a delete forgets its rows for good (`forget`: their bytes overwritten, the WAL checkpointed); and when its database has just taken its rows over from the archive, the core pushes them whole at that start. Its `events.rows()` is what a rebuild puts back for it and what `calendar check` compares. Friend map pushes its own (`modules/friend-map/server/calendarPush.ts`: after its imports through `apply`'s rows, after the people rules and after a changeset that touched what its rows read, through `push` and `replace` with a scope) and answers its hooks (`events`); the core pushes and answers only for its own conversations with agents (`eventIndex.ts`, `coreOwners`).

**A module whose store is its own code's.** Rituals' store is rituals' own SQLite database, with its own schema versions, migrations (`bin/ritualctl --migrate`), journal mode and backups, written by its own command outside the server: not a `database` for the core to open in WAL mode and migrate. So the module declares none, reads the store in-process and read-only through rituals' own view (`modules/rituals/server/view.ts`) wherever the core would ask its database (its route, its rows, its service), keeps the calendar in step with a watch (`work`), tells the NAS backup what to take (`backup`), and leaves `npm run archive -- backup` out (that copies the databases the core opens; rituals keeps a backup before each of its own writes). Where the store is, ritualctl is told by rituals' own `RITUAL_ROOT` or its `config/root` (`modules/rituals/README.md`), and the module reads it at `modules/rituals/` of the archive's folder: the two must agree, which the migration that moves the store sets up once.

**Editing a table** (`server/edits/`; console.md's "Editing"). The captain: "I would want to be able to edit tables directly from wherever I'm looking at a table", the same table with the same permissions everywhere, so permission is the table's and the field's, never the page's. A table declares the fields it lets be edited beside its definition (`sourceTab`'s `edits`: each field's key, a column's or a drawer field's, its label and how it is written, `viewer/editWire.ts`'s `EditField`, which also bounds what it takes), and its module gives an editor for it (`edits`): what a row's fields are now (a field this row keeps as it is `locked`, saying why: an imported call's time), how a value is written, how an edit is undone, a note's words and a people field's choices; and, for an editor whose state is slow to read row by row, `locked`, which fields of each of a page's rows stay as they are in one go (the grid asks once a page, `GET /life-archive/api/edits/locks`, to edit a cell in place only where its row lets it: friend map's Calls from a call's key, rituals' on one read of its view, exercise's on one read of its index; left out, each row's state is read), and, for an owner whose own change log keeps its edits, `undone` (`undoneInLog`: whether an edit's changeset stands undone there, so the core's record reads it from the log and never disagrees with it). The core's one edit route (`/life-archive/api/edits`, `server/edits/http.ts`) finds the row by the table's own id for it (its calendar row's; for a table whose rows are not in the calendar, its editor's `rows`, `OwnTableRows`: friend map's People and Tags, found by a person's or a tag's own id), hands the edit to the row's own owner, refuses a field the table does not let be edited or this row keeps (403) and a value the field does not take (400), and keeps every edit in its record (`core.sqlite`'s `table_edit`: who, when, the row, the field, what it was and became, never a note's words, and the owner's receipt), which `npm run archive -- edits` reads and `edits undo <n>` undoes through the owner. An editor writes through its own path and pushes the row into the calendar itself: friend map through its changesets (its change log is the undo), exercise as corrections beside the copies Polar gave (`workout_correction`, `workout_note`, under a change log of its own over its database, the core's `Changes` given the module's tables), which every read of its index takes over them, so a re-import never undoes them and the calendar's rebuild from the module gives the corrected rows back; rituals through ritualctl's own requests, its receipt keeping what the habit was and the doings removed, for an undo that puts both back. **Adding and deleting rows.** The captain answered "add and delete rows from a table?" with yes, for his own records only: a table whose rows are partly his own records says so beside its definition (`sourceTab`'s `own`, `viewer/editWire.ts`'s `OwnRows`: the fields Add asks, which may be more than its `edits`, such as what a call was on, and which rows can be deleted, in words), and its editor gives `add` (a new row from those fields, its key in the calendar and a receipt), `remove`, `kept` (why a row is never deleted: an imported call's "its source's"; null for one of his own) and `undoRow`, each through its own write path as an edit is. The route takes them at `POST /life-archive/api/edits/add` and `/delete` (403 for a row its owner keeps, or a table with no `own`), and keeps each in the same record as an add or a delete (`table_edit.action`, its field empty and the row's fields as before or after), undone the same way; an imported row is never deleted. Friend map's Hangouts and Calls take them (`modules/friend-map/server/tableEdits.ts`), and its People (someone added by hand, never anyone with accounts) and Tags (never a built-in one; `modules/friend-map/server/peopleEdits.ts`). An add the owner would have him be sure of (someone already goes by the name) is refused with 409 (`UnavailableError`), and Add then offers **Add anyway**, which sends it again with `anyway`. Besides a time, numbers, a choice, people and a note, a field may be a short text (`text`, `long` for a few lines) or tags (`tags`, several words in order), either offering the table's own values as they are typed (`suggests`: the editor's `options`, as a people field's). A module's test drives it as the server does (`sdk/testing.ts`'s `edits()`).

`viewer.tsx` exports `defineViewer({...})` (`sdk/viewer.ts`'s `ViewerDefinition`): its `aspects` (each a place in the rail, in the registry's own shape, `viewer/console/registry.ts`, its icon one the console names or a drawing of its own, `IconDrawing`), its `views` (each under one or more aspects) and, when a place of its has moved to another page, `moved`: the old address's steps to the steps of an address that opens it now (friend map's `"friend-map/messages": "events/messages"`, its Messages tab, now a table of Events' Tables), so an old address opens the new place with its query as it was (`viewer/console/moved.ts`; `registryProblems` refuses a move from a place a view is still at, or to one no view answers to); and `saved`, told of each field edit saved on the Events page's Tables, as the record keeps it (`viewer/savedEdits.ts`), for what a module keeps in the browser that follows its rows (friend map's Hide carries a tag renamed in its Tags table over to the new name). A module's page draws no table: its tables are its server half's (`tabs`), shown and edited on the Events page's Tables.

**A module's own settings** are its section of `settings.json`, the top-level key its id names (settings.md's "A module's own settings"): the core passes a key it does not know that names an installed module through, and the module reads it with `sdk/server.ts`'s `moduleSettings(id, schema)`, as strictly as the core reads its own. A module reading them as its `module.ts` loads is broken, saying why, when its section is not what its schema says. **A view may sit under another page's aspect**, a core one included: a view listing `"events"` among its aspects is a tab on the Events page, after the core's own tabs unless it gives an `order` (a number on the view, `View.order`: the smaller first, a view with none after every ordered one), at `/life-archive/dev/events/<section>`, as rituals' Daily rituals is (`/life-archive/dev/events/daily`); `registry.test.ts` keeps that so. Rituals' Daily rituals is `order: 2`, between the core's Calendar (1) and Tables (3), before Sources (4).

`demo.ts`, when the module is in the public demo, exports `defineDemo({...})` (`sdk/demo.ts`'s `ModuleDemo`; docs/demo.md): what the demo's page runs of its server over the made-up databases, found by its place as `viewer.tsx` is: its `tabs` (the same as `module.ts`'s, which `viewer/demo/backend.test.ts` holds), the connection they read (`tablesRead`), its calendar rows' `owner`, and any `routes` it answers live (friend map's chat a Messages row opens). A page left out of the demo takes its module's tabs on the pages shown with it.

## How the core finds and loads a module

- **The server** (`server/modules/loader.ts`, `server/modules/store.ts`): at start, before the archive opens, it lists `modules/*/` for a `package.json` with `"lifeArchive": true` (one that parses and does not say so is no module, and is passed over without a word), imports each `module.ts` that the settings leave on, checks its id and SDK major, opens the database of each that declares one (and runs its take-over, once), and says what it found (`Modules on: exercise, folder-history, friend-map, health, journal, rituals, shopping`). Then it opens the archive, which takes the modules' events and tabs (`archive.modules`): the calendar's rebuild and check read their `rows()`, the Events page's tables are the core's then theirs, and the host runs their connectors beside its own, each module's as a ledger of its own (`server/connectors/host.ts`: its imports applied by the module's `apply` to the module's database, its spool files named by it). It builds the modules' services into one Layer below the HTTP server (`server/serverLayer.ts`), then starts each module's `work` in a fiber of its own, mounts each module's route at `/life-archive/api/m/<id>` and at its `mounts` with the same services as the core's routes, serves each module's `page`, and tells the page each module's switch (`GET /life-archive/api/settings`, `modules`). A folder whose `package.json` cannot be read or parsed, or a module whose `module.ts` cannot be imported, which names another id than its folder or another SDK major, or whose database cannot be opened, is **broken**: listed, said so in the log, skipped, and off for the page, as a broken connector manifest is skipped. The modules' databases are closed after the archive.
- **The page** (`viewer/modules.ts`): Vite finds every `modules/*/viewer.tsx` by its place as the page is served (`import.meta.glob`, lazy), the page loads the `viewer.tsx` of each module the server says is on before the console loads (`viewer/main.tsx`, as it sets the page's settings), and the registry (`viewer/console/registry.ts`) adds each module's aspects and views to the core's; a module with no `viewer.tsx` (journal) adds nothing, and the console is as it was. The rail's order is `RAIL`, the captain's, by key, so a module's aspect sits where he put it (Health Record third, Fitness fourth); an aspect `RAIL` does not name follows the named ones. The server is the one source of truth for what is on: what the console shows leaves out a module the server said is off or broken, its views with it, wherever they sit, and a module the server did not name is off, so a folder with a `viewer.tsx` the server does not count as a module shows nothing. A module that is off is never loaded, so nothing in its `viewer.tsx` can reach the console. A `viewer.tsx` Vite cannot resolve, as its folder's `package.json` does not parse, declares nothing (`vite.config.ts`: Vite resolves every module's `viewer.tsx` as it serves `viewer/modules.ts`, loaded or not, and would otherwise fail every page); the server has said that module is broken and off anyway. Likewise Vite's scan for the packages to bundle ahead, which reads every module's files, loaded or not, reads one that does not parse as empty rather than failing whole and leaving the page with no packages (`vite.config.ts`'s `moduleScanFallback`). A module that is on but whose `viewer.tsx` cannot load (a syntax error, a name the SDK no longer exports, no default export of `defineViewer`'s shape) is a page of its own in the rail at its id, saying it did not load and why (`viewer/console/ViewFailed.tsx`), and every other page goes on; and a view that throws as it is drawn shows why in its own place, the rail and every other page unaffected. `server/vite.test.ts` holds both: a broken `viewer.tsx` of a module off, and an on module's that fails.
- **The guard's review and the testing data** load every installed module, switched off or not (`loadModules({ all: true })`), **the written documents** every one git tracks: a module's privacy lines and made-up data are about what the archive may hold, not what runs. A module broken among them is said so, as its privacy lines are then missing (`installedPrivacy`). The NAS backup loads every one too, and one that does not load stops `npm run nas-backup` and its `verify`, rather than a snapshot taken without that module's own databases and excludes (`server/archive/nasBackup.ts`'s `moduleKept`).

## Switches

In `settings.json` in the archive's folder (`docs/settings.md`):

```json
{ "pages": "all", "modules": { "exercise": false, "shopping": true, "inspirations": true } }
```

- `modules` switches a module on (`true`, for an unfinished one; "Ready pages" below) or off by id. Off, it is listed but not loaded: it is listed but not loaded, its database is left closed as it is, its routes answer 404 (friend map's `/api/archive/` and `/friend-map/` with them), its connectors are not run or listed (the Sources tab and `connectors` know nothing of them), its work does not run, its services are not offered (the Fitness page shows no workout logged in Rituals with rituals off), its tables are not on the Events page (the Calendar view shows the kinds the server has tabs for, so its chip goes too), its rows stay in the calendar as they were, out of sight without its tabs and left alone by `calendar check` and `calendar rebuild`, so its pushes go on from there when it is on again, and its page is not in the rail. A module not named follows its ready mark and `pages`. A key naming no installed module is said so on stderr by the server and any `npm run archive` command that opens the archive, the callers that pass the switches (the documents, the testing data and the guard load every installed module and pass none), and switches nothing: `settings.json` is every checkout's, so it may switch a private module another checkout has, and a misspelt id never switches nothing off in silence. A view on another module's page goes with that page: with `exercise` off there is no Fitness page, so rituals' Habits tab (the weekly targets) has no page, and nothing stands in for it.
  A switch is the server's and the page's alone: **switching a module off does not uninstall the jobs it installed outside the server** (its launchd agents: journal's voice journals and Grok calls, friend map's mac-imports and cua-exports), which run on as before. To stop one, uninstall it with its module's command where it has one (`npm run journal -- uninstall`, `npm run journal -- grok-calls uninstall`), else unload its launchd agent (`launchctl bootout`). Having a job honour its module's switch is a later step.
- Events, the home, has no switch, and every other page is a module's. The core's pages that became modules were switched in `aspects` before, which is no setting any more: Shopping's old `aspects.shopping` and Inspirations' `aspects.inspirations` are read as `modules.shopping` and `modules.inspirations` from the archive's `settings.json` by every entry point, in memory, and written back into the file when the archive's server starts (`server/movedSwitchUpgrade.ts`, saying so on stderr; an `aspects` left empty goes), and `aspects` is refused in a settings file named by `LIFE_ARCHIVE_SETTINGS`, saying where it went.
- `pages` is `"ready"` (the default) or `"all"`: what a page not named in `modules` follows.

### Ready pages

Every page this repository ships carries a ready mark, so what a new archive offers is decided page by page, not by
which branch its code is on. A ready page is on in a fresh install; an unfinished one is off, out of the rail, its
module not loaded, until its owner switches it on by name or sets `"pages": "all"`. The marks:

- a module's: its `package.json`'s `"lifeArchiveReady": true` or `false` (`server/modules/loader.ts` reads it before importing anything);
- Events, the core's one page, the home, is always on and has none (`src/pages.ts`).

Ready today: Events and Friend Map, and the folder history, which has no page (the core ran it for every archive before it was a module, and with no folders named it does nothing). Promoting a page is that one line. `src/pages.test.ts` holds every module the
repository ships (those `.gitignore` names) to saying its mark either way. A private module has no mark, and is on, as
it always was: the mark is for this repository's pages, not its owner's. The public demo (docs/demo.md) reads the
same marks, so it shows what a fresh install shows. The testing data's `settings.json` says `"pages": "all"`, so the
tests and a server on it see every page.

An archive made before the marks had every page on, and an upgrade switches none of them off: the first process of
the new code to read its settings writes `"pages": "all"` into a `settings.json` that says nothing of `pages`
(`server/readyPagesUpgrade.ts`, saying so on stderr). What tells it from a fresh install is its core's database: the
code that knows the marks marks `core.sqlite` (`ready_marks` in its meta) the first time it opens it, so an older
archive is one whose `core.sqlite` lacks the mark, or one still on the layout before `core.sqlite`. Taking the key
out afterwards leaves only the ready pages on, as in a fresh install.

## The seams between the modules and the core

- **Health asks exercise for the highest heart rate.** The Fitness page's activities are a service of the exercise module (`modules/exercise/server/service.ts`'s `Exercise`: `peak`, the highest heart rate a trusted recording holds, with the page it was recorded on), declared in its `module.ts` and offered through the SDK; health's route asks for it optionally (`Effect.serviceOption`), so with exercise off the Health tab shows none.
- **Exercise shows the runs transcribed by hand**, which are kept in health's `by-hand.json`. Health offers them as a service the SDK names (`RunsByHand`), and exercise asks for it optionally: with health switched off there are none, and the Fitness page shows every other source's activities as before. A delete is whole or refused, so while those runs are unknown (health off, or its `by-hand.json` not readable, when `runs` fails) no activity can be deleted: a copy of it may be among them, and the page says so in place of the button. The core never reads health's file.
- **Exercise shows the workouts logged in Rituals.** The rituals module offers them as a service the SDK names (`RitualWorkouts`, `modules/rituals/server/service.ts`: each day's workouts as rituals' view shows them, read from its store at each ask, with the minutes their words state, whether they say zone 2 and their sport's family), and exercise asks for it optionally: with rituals switched off there are none, and nothing in exercise changed when the service moved from the core to rituals. It offers a second, `RitualHabits`: how each day's habits stood, statuses alone, which Fitness's Bryan Johnson tab counts (stretching as mobility, the plank as balance when asked); with rituals off that page has no habit days, and says those pillars are unmeasured.
- **A module that was a part of the core** keeps its addresses: friend map's contract is at `/api/archive/` as it was, its page at `/friend-map/`, its commands `npm run archive`'s, its tables' kinds and its calendar rows keyed as before. Its archive was moved once, not taken over: `npm run archive -- migrate friend-map-module` (`server/archive/migrate.ts`, with the server stopped; a dry run, then `--apply`) backs up the archive, copies the core's tables out of it into `core.sqlite` (counts checked), the trail of content reads into the calendar when it has it not, moves `archive.sqlite` into `modules/friend-map/`, drops from it what is no longer its own (the core's tables, and exercise's and rituals' old rows), and only then puts `core.sqlite` in place (it is built as `core.sqlite.partial`); until then nothing opens the folder. It refuses an archive whose schema is not the one friend map had when it moved, and while another process holds the archive open; a move interrupted at any step is finished by running it again. And exercise's take-over copied the archive's workout events and their detail, its tombstones and the polar connectors' runs and cursors into its database with their ids, so every activity's page and the live connector's place went on unchanged; the archive's rows of them stay until the core's `npm run archive -- migrate friend-map-module --apply` (the friend map step's move, which drops them too) overwrites them for good (`server/archive/legacy.ts`), which is refused until the module's database has taken them over and holds them all (`npm run exercise -- status` shows what it holds). Rituals took nothing over: its store was always its own, and the archive's rows of it were the rituals connector's index of that store, which the module's rows replace keyed the same (so the calendar's rows went on unchanged); they stay until `npm run archive -- migrate friend-map-module --apply` (the friend map step's move, which drops them too), refused until the store is in the archive's folder for the module to read in their place. The inspirations' routes kept their address (`/life-archive/api/inspirations`, a mount, where the iPhone's shortcut posts its captures), their commands are `npm run archive`'s, and their items' numbers and changesets kept their ids: their take-over (`modules/inspirations/server/db.ts`, from `core.sqlite`, its `takeOverFrom`) copies every table of theirs and their change log row for row, and their kept files from `platform-exports/inspirations/live/` into `modules/inspirations/files/`, each copy checked byte for byte, and checks before it commits that every table holds exactly the core's rows; the core's tables and files are left where they were, read by nothing, until the captain says they may go.

## Tests, fixtures and documents

- `npm test` runs every module's tests with the core's (`vitest.config.ts` includes `modules/*/**/*.test.ts`), and `npm run typecheck` checks them (`tsconfig.json` includes `modules`). A module's tests use only made-up data (`server/fixtures/madeUpNames.ts`'s pools, which its test holds the modules' tests and fixtures to as well). A module with a store tests through `sdk/testing.ts`'s `testingLifeArchive(folder, definition)`: a life archive on a testing folder with the module loaded as the server loads it (its database open, its connectors in the host, its rows in the calendar, its services built), to import through the host, read its own index and check the calendar; `sdk/sdk.test.ts` holds that file to tests. Rituals' own tests (`modules/rituals/tests/`, rituals' repository's) run with the rest, on its made-up fixtures, a few of them running `bin/ritualctl` in a temporary copy of its sources.
- `npm run testing-data -- <folder>` writes every installed module's made-up data into the folder with the core's (each module's database opened for its `fixtures.write`), so a server on it shows every page.
- `npm run docs` writes `docs/privacy.md` with the privacy lines of every module git tracks, and each document a module git tracks writes (`documents`): friend map's `docs/platforms.md`, from its chat connectors' manifests; `tools/docs/docs.test.ts` fails until it is run and committed. The guard's review is told the privacy lines of every installed module, a private one's too.
- A module's command is an npm script in the root `package.json` pointing into the module (`"health": "node --no-warnings modules/health/cli.ts"`, `"exercise": "node --no-warnings modules/exercise/cli.ts"`, `"journal": "node --no-warnings modules/journal/cli.ts"`, `"rituals": "node --no-warnings modules/rituals/cli.ts"`), which imports `sdk/command.ts` first; `server/onSettings.test.ts` holds it to stopping on a settings file it cannot use, as every entry point must. A private module, which no tracked file may name, runs its `cli.ts` through `npm run module -- <id>` instead ("Private modules" below). A command that reads the module's database opens it read-only on a connection of its own (`npm run exercise -- status`): the schema is the server's to bring up to date. Rituals' own commands (`modules/rituals/bin/`) are rituals', not npm scripts: they run on the Node their `config/node` names, as they did in rituals' repository, and never import the SDK.
- **A module's job outside the server** (friend map's mac-imports and cua-exports, journal's voice journals and Grok calls): a standalone scheduled command, kept in the module's `jobs/<job>/` (its run, its installer, its state and its platform's parts; friend map's command files sit beside theirs, `jobs/mac-imports.ts`), never in `server/`, which is for what runs inside the server (routes, stores, services). Its launchd agent is one the module's command installs and removes, written with what the SDK exports of `server/jobs.ts` (the plist, `installLaunchAgent`, `removeLaunchAgent`, the launcher Full Disk Access is given to, `buildLauncher`, which builds the core's `server/launcher.c` to run the module's command, and the lock, `takeLock`), and it tells someone through the notifier, `Notifier` (`server/notifier/notifier.ts`). A job that moves keeps its agent's label, and the path its installed agent runs keeps working until the agent is written anew (rituals' `bin/ritual-voice-calls`, for the Grok calls job that was rituals'). The agent is launchd's, not the server's: a life archive without the module has none, since only the command installs it, and one whose owner switches the module off keeps it until `npm run journal -- uninstall`. Its state (journal's ledger) is in the module's folder of the archive's folder, `modules/<id>/`, as a module's database is.

## Private modules

Every folder under `modules/` is ignored by git (`.gitignore`'s `/modules/*`), so a module cloned in whose code is not this repository's, a private one, is never committed by accident; a module built in this repository is named there to track it (`!/modules/health/`, `!/modules/exercise/`, `!/modules/journal/`, `!/modules/rituals/`, `!/modules/friend-map/`, `!/modules/shopping/`, `!/modules/folder-history/`; rituals' per-installation `config/`, and a store kept beside its code when nothing names another place, are ignored under it). Nor does a private module reach a tracked file: `docs/privacy.md` holds only the modules git tracks, and only a tracked module's documents are written, so they read the same in every checkout, and the lockfile knows no module. When a module is split into a repository of its own (the plan's M7), its line goes and its folder is a clone.

A private module is what a module of this repository is, with nothing of it in a tracked file:

- **Its folder is a real one**, a clone (or a copy), not a link to a folder elsewhere: Node, Vite and TypeScript each follow a link to where it points, and from there neither `../../sdk/` nor the root's `node_modules` is found.
- **Its command** has no npm script of its own (the root `package.json` is tracked): `npm run module -- <id> [its arguments]` runs its `cli.ts` (`server/moduleCommand.ts`), on the pinned Node and the settings, as every entry point.
- **Its settings** are its section of `settings.json` and any keys of its own in `.env.local`, both listed in its README; its page is told what it needs through `viewerSettings`.
- **Its page** follows the pages the rail names (`RAIL` names none of it), and its icon may be a drawing of its own.

## Trying a change

Build a testing folder and run a server of your own on it, on a spare port, as running.md's "Running" says; every module's made-up data is in it, each module's database under its `modules/<id>/`. To see a module switched off, add `"modules": {"<id>": false}` to the folder's `settings.json` and start the server again: the log says `off: <id>`, the rail has no page for it, `/life-archive/api/m/<id>` answers 404, its tables are gone from the Events page and its connectors from Sources.
