# Logging rules

These are rituals' own rules for whoever logs through `bin/ritualctl`, under the repository's root `AGENTS.md`; `HANDOFF.md` has every request.

- **One authoritative store.** `bin/ritualctl` is the write interface; `data/ritual.sqlite3` under the store's root is authoritative. Backup copies elsewhere are frozen (a `data/FROZEN_BACKUP.json` marker makes their CLI refuse writes). Preserve evidence, audit, exports and backups; never rewrite historical paths to make them look current. Missing storage is an error, never a new empty production store: `bin/ritualctl --init` is only for setting up a brand-new installation. Never use ad-hoc SQL writes.
- **Taking turns.** For logging: read the record, preserve the original source ID and intent, use the CLI, and retain its acknowledgement. Database transactions, exact-payload idempotency and revision guards support sequential agents.
- **Dates.** The store uses one IANA timezone, including DST: `TIMEZONE` in `src/instants.ts` (`RITUAL_TIME_ZONE`, else the life archive's `settings.json` `timeZone`, else the machine's, with a warning; README.md). Ritual date, message receipt, actual check-in and actual activity/completion time are different. Preserve exact words, original message ID, receipt timestamp and any disclosed contextual date interpretation in `source_text`. Unknown occurrence stays unknown. Each evening closes at 06:00 the next day in the store's timezone: 00:00–05:59 belongs to the previous day, 06:00 starts the new one. After-midnight continuation can belong to the previous evening when context supports it; disclose and preserve that inference. The active day closes early once every applicable habit is done, with answers still editable until that 06:00 close; un-ticking reopens it. N/A and open days are excluded from rates. Query `ritual_status` and exceptions; don't reimplement cutoff rules in chat.
- **Habits.** Nullable magnesium/protein/stretching/journalling/wind_down, numeric plank seconds and notes. wind_down is asked from logical date 2026-11-09 (`HABIT_SINCE`); earlier days take no answer for it. Merge reported subsets; omitted fields stay intact and unknown stays null. Do not invent duration from a bare plank completion. Each reported doing of a habit is a habit event under the daily tick (`ritual_put` `events`, HANDOFF.md "Habit times"). Record `done_at` only when the user states or clearly implies the time ("took magnesium at 9": `user_stated`, resolved to an offset-bearing instant in the store's timezone on the logical date); "just took protein" uses that message's receipt instant (`message_received`, the same instant as source_text's "Received at"). Otherwise the basis is `unknown` and `done_at` null. Never take a scheduled ping's, invitation's, processing or write time as the activity time. A restatement of an already-recorded doing is not a new event; a second dose is. A time stated later for a past day is a fresh report on that date (or `correct` of its unknown-time event); past days get no invented events.
- **Check-ins.** An explicit check-in establishes a new checkins entry. A journal can supply a default only when the installation's policy authorizes it: use the original journal timestamp and the atomic `journal_entry_at` option in HANDOFF.md. Ordinary habit/workout reports and scheduled pings do not establish check-in. If the exact check-in instant is unknown, a receipt-based entry must be explicitly qualified as receipt time in source_text. Never label it verified physical arrival.
- **Requests.** Stable request_id per action; use the original message ID and stable suffixes for multiple actions. Lost acknowledgement: retry the identical payload/ID. A changed payload with the same ID is rejected. Corrections need a fresh ID, a reason and the latest entity expected_revision. On conflict read/reconcile; never force or silently drop a pending input.
- **Workouts, reminders, notes.** Workouts have exactly id, date, type, details, title: `type` is the category (lower-case, open text; "bike ride"/cycling fold into `bike`, running into `run`), `title` a short glanceable label, explicit or derived only when the details state the duration/distance, else null; multiple rows/date are allowed; details are free text. Distinct active days and workout counts differ. Reminders are independent; a scheduled review doesn't replace earlier explicit timing. Querying due items doesn't deliver them; delivery and completion are separate states. Notes retain topics and chess-clock notation. Preserve original legacy midday checkpoints separately; never turn them into new evening check-ins.
- **Temporary items.** Temporary ritual attachments have their own definitions and date-keyed nullable answers, not core columns or standalone reminders. Use `ritual_checklist` with explicit ritual identity/date or the enriched `ritual_status` to present the whole ritual. Required checks participate in `full_completion.complete`; reminder-only items have no tick. Core rates and the dashboard stay core-only. Expiry excludes future dates, never removes historical unanswered checks; do not invent earlier answers or extend expired contracts. An attachment's optional ISO `weekday` (Monday 1–Sunday 7) restricts its logical-date scope. Sunday weekly checks are required evening attachments, answered on that Sunday for its Monday-to-Sunday week. No answer comes from activity/food mentions.
- **Routine behaviour.** Respect earlier reports, no minimum duration, lectures, scorekeeping or schedule announcements, and do not log a scheduled invitation as an observation. An invitation/checklist includes applicable attachments in the same ritual message. Claim the full ritual complete only from `full_completion.complete`. Schedules and reminder wakes belong to the assistant that relays the owner's messages, not to this store.
- **Offline.** When the Mac is unreachable, the relaying assistant holds the original messages durably; don't claim a database save. Local enqueue (`--enqueue`) acknowledges only the queue; replay (`--replay`) stops on conflict.
