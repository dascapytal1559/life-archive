# The rituals module

The captain's daily rituals and weekly targets, which his assistant logs for him through `bin/ritualctl` into rituals' own store, shown as rows of dots on two tabs of other pages (Events' Daily rituals, `/life-archive/dev/events/daily`, and Fitness's Habits, `/life-archive/dev/fitness/habits`; there is no Rituals page since 7 November 2026), with each habit done and each day's standing on the Events pages' calendar and the workouts he logs there on Fitness's Activities. The daily ritual's habits are magnesium, protein, stretching, the plank, journalling and, from 9 November 2026, wind-down, which is due by midnight and drawn green or red against it (HANDOFF.md's "Wind-down"). The core's README says how it all works ("Rituals", "The calendar"), and how a module is laid out, found and switched (`docs/modules.md`).

It is the fourth module (the journal's half of the same step landed first that day), and rituals' own code: the rituals repository's `bin/`, `src/`, `tests/` and `HANDOFF.md`, brought in on 6 November 2026 as they were (the store, its reviewed migrations, its Python-compatible hashes and its Effect 4 code untouched; its retired dashboard server, menu-bar app, browser checks and screenshots left behind), with the module's two halves beside them. Its voice-calls agent followed on 7 November 2026, when the repository was retired, and went on to the journal module on 8 November 2026 (below, "Voice calls"). `bin/` and `src/` are as they were but `src/root.ts`, `bin/node.sh` and the five wrappers. Rituals' tests changed too: `tests/helpers/fixtures.ts` finds the root's `node_modules`, for the three tests that link it (`tests/weekly-targets.test.ts`, which changed no further, and the two next); `tests/ritual-view.test.ts`, whose oracle was the retired dashboard server, now holds hand-counted expectations from the fixture bundle; and the wrapper list of `tests/node-resolution.test.ts` lost the retired commands, and it passes the store's root explicitly. The core loads `module.ts` (its server half) and `viewer.tsx` (its page half), and the module imports the core through the SDK alone (`../../sdk/`); rituals' own code imports nothing of the core.

- `bin/`: rituals' commands, run on the Node their `config/node` names (`bin/node.sh`): `ritualctl`, the one write path (one JSON request on stdin, one acknowledgement on stdout; `HANDOFF.md` has every request), `ritual-view` (the read-only view, as JSON), `ritual-agent` (cooperative edit claims), `ritual-dashboard` (the static snapshots) and `ritual-voice-calls`, the voice calls' old command, which hands its run to the journal module (below, "Voice calls"). They find the store as `src/root.ts` says: `RITUAL_ROOT`, else `config/root`, else beside the code.
- `src/`: the store (`store.ts`: schema, validation, idempotency, revisions, audit, backups, import, export, restore, and running the reviewed migrations, whose steps are `migrations.ts`), the rules (`applicability.ts`, `habitEvents.ts`, `deadlines.ts`, `attachments.ts`, `weeklyTargets.ts`, `instants.ts`, `encoding.ts`), the write client and queue (`localClient.ts`, `locks.ts`, `files.ts`), the dashboard's projections (`dashboard.ts`, `dashboardWeb.ts`, `dashboardTheme.ts`) and the view other programs read (`view.ts`), and in `bin/` the entry point behind each wrapper.
- `tests/`: rituals' own tests, on made-up fixtures (`tests/fixtures/`), run with the life archive's `npm test`.
- `AGENTS.md`: rituals' logging rules, for whoever logs through `bin/ritualctl`.
- `module.ts`: no `database` (the store is rituals' own, below); its route (`server/http.ts`: `GET /life-archive/api/m/rituals`, the whole view, and `.../dashboard`, what rituals' own dashboard served); the `RitualWorkouts` and `RitualHabits` services the exercise module asks for optionally (`server/service.ts`: the workouts logged, and each day's habit statuses alone, for Fitness's Bryan Johnson tab); its rows in the core's calendar and its answers for them (`server/calendar.ts`); the watch that keeps those rows in step with the store (`server/watch.ts`); the Rituals and Ritual days tables (`server/habitsTab.ts`, `server/daysTab.ts`), which the Events page's Tables lists, and their editor (`server/edits.ts`: a habit's day set done or not, through `ritualctl`'s own requests); its made-up store for the testing data (`fixtures/rituals.ts`); its lines of the privacy policy (`server/privacy.ts`); and what the NAS backup takes of its folder (`backup`).
- `viewer.tsx`: no aspect of its own, two views on others' pages: Daily rituals on Events and Habits on Fitness (`viewer/HabitViews.tsx`), each habit or target a row (`viewer/dots.ts`): Daily rituals as their whole run, today carved out at the left and the days before it running newest first (`viewer/RunRows.tsx`, `viewer/run.ts`, `viewer/run.css`), Habits as rows of dots (`viewer/DotRows.tsx`, `viewer/dots.css`), with one tooltip (`viewer/pointing.tsx`).
- `wire.ts`: the view's shape as the page reads it and the module's addresses, shared by both halves.
- `cli.ts`: `npm run rituals -- status`, where the store is and what it holds; `npm run rituals -- voice-calls ...` says the job is the journal's now (below) and does nothing.

**Its store** is rituals' own SQLite database, `data/ritual.sqlite3` under rituals' root, which in a life archive is `modules/rituals/` of the archive's folder (`~/life-archive-data/modules/rituals/data/ritual.sqlite3` for the captain's): `bin/ritualctl` writes it, as G and firstmate log through it, keeps a backup before each write in `data/backups/`, its exports in `data/exports/`, the dashboard snapshots in `data/views/` and its offline queue in `queue/`; the module reads it in-process and read-only through rituals' own view (`server/view.ts`: `src/view.ts`'s `readView`, every rule applied by rituals: the 06:00 cutoff, what applies on a day, how a check-in's time is known) each time the page, the calendar or the Fitness page asks. It is not a database the core opens (that would put it in WAL mode and run migrations of the core's; rituals keeps its journal mode `delete` and runs its own, `bin/ritualctl --migrate`), so `npm run archive -- backup` does not copy it; the NAS backup sends a checked copy of it each night, at its own path in the snapshot (`/modules/rituals/data/ritual.sqlite3`), and leaves rituals' own backups out. **Where the store is** must agree on both sides: the module reads `modules/rituals/` of the archive's folder, and ritualctl is told by `RITUAL_ROOT` in the environment or the first line of `config/root` beside the code (both ignored by git; `HANDOFF.md`'s first section), else keeps the store beside the code, as a fresh copy of rituals' sources does (the tests make one). A life archive's installation writes `config/node` and `config/root` once.

**Its time zone.** The store reckons its days (each closing at 06:00 the next morning) and writes its instants in one IANA zone (`TIMEZONE`, `src/instants.ts`): `RITUAL_TIME_ZONE` in the environment, else the life archive's own zone, `timeZone` in the `settings.json` two folders above the store's root (the archive's folder, whose `modules/rituals/` the store is), so the calendar's days and rituals' agree, else the machine's, with a warning on stderr each time the code loads, since a machine that changes zone (travelling) moves the 06:00 close. Name the archive's zone once, before the store's first day: a store keeps the zone its days were reckoned in, and a different one later moves every day's bounds. (`config/timezone`, which named it before, is read no more.) The tests run in `Australia/Melbourne` whatever the machine's (`vitest.config.ts`).

The assistants that log through `bin/ritualctl` read the store through its read requests and `bin/ritual-view`, without the archive's trail, as rituals' own contract has it (`docs/privacy.md`): the store's audit records every write, and the archive's content commands never reach it.

**In the calendar**, the module's rows are each habit done as a moment (keyed on rituals' own id, `habit/<id>`; a habit a day ticks done with no doing of it, `tick/<day>/<habit>`, at its day's midnight; a plank as long as its day's cell says) and each day rituals shows as a summary of which habits, and which required checks that applied that day (by id), were done, not done and not reported yet (`day/<day>`), the same rows keyed the same as the rituals connector pushed before the module, so the Events pages read what they read. Since ritualctl writes the store outside the server, the watch (`server/watch.ts`, the SDK's `work`) looks at the store's file every 20 seconds while the server runs and pushes the rows whole when it changed, or every five minutes regardless (the view moves with the clock), and at once as the server starts; it says in the log what changed, and once when the store cannot be read, leaving the rows as they were. With no store there (an archive without rituals, or one whose store has not moved in yet) it pushes nothing.

**Voice calls.** The job that copies each finished call still in Grok Bot's cache into the vault's journals, as HANDOFF.md's "Journal contract" lays them out, is the journal module's Grok calls job since 8 November 2026 (`modules/journal/jobs/grok-calls/`, `npm run journal -- grok-calls`; the journal's README, "Grok calls"): it writes into the journal, not into rituals' store, so it went to the module the journal is. Its files, their layout and its launchd agent's label, `local.life-archive-voice-calls`, are what they were. Two of rituals' old ways in stay for now: `bin/ritual-voice-calls --cache DIR --journals DIR --provider SLUG`, which the agent `npm run rituals -- voice-calls install` wrote runs by its path, hands its run to the journal's command on the same Node (`bin/node.sh`), so that agent goes on without being installed again; and `npm run rituals -- voice-calls ...` says where the job went. Once `npm run journal -- grok-calls install` has written the agent anew with the journal's own program, nothing runs the wrapper, and both go.

**Its private notes** are in the archive's folder, never here: `modules/rituals/LOCAL.md`, this installation's policies that HANDOFF.md names (which journal folder and provider slugs, whether a journal sets a default check-in), and `modules/rituals/history/`, what the rituals repository kept beside its code when it was retired (its open threads, priorities, planning, thread history, evidence, private devlog, and the whole repository as `rituals-repo.bundle`).

Switch the module off with `"modules": {"rituals": false}` in the archive's `settings.json`: its two tabs, the Rituals and Ritual days tables and the chip, the routes, the watch and the `RitualWorkouts` and `RitualHabits` services go with it, its rows stay in the calendar out of sight, and `ritualctl` goes on unaffected: it is rituals' own, never the server's. The archive's rows from before the module (the rituals connector's `ritual_*` events and its runs) stay until `npm run archive -- migrate friend-map-module --apply` (the friend map step's move, which drops them too) overwrites them for good, which is refused until the store is in the archive's folder for the module to read in their place.
