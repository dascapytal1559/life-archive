# The journal module

The life archive's journal: the captain's journals, notes and drafts, where he keeps them in an Obsidian vault (`Vault` in the archive's folder; it can be a link into iCloud Drive, say, so that Obsidian on the Mac and on the phone both edit it); the voice journals transcribed into it on the Mac each day at 06:00, every recording Voice Memos has synced since and he has not deleted, ready for the agent that writes each day's clean journal (firstmate, where it is set up); and, where he uses Grok Bot, the voice calls with it, copied into the vault from the app's cache as they end. docs/data.md's "Where the data lives" says how the vault can be kept, docs/features.md's "Voice journals, transcribed at 6 AM" how the transcription runs, and `docs/modules.md` how a module is laid out, found and switched.

It runs inside a life archive, never on its own: the core loads `module.ts` (its server half) and `viewer.tsx` (its page half, the Journal page), and the module imports the core through the SDK alone (`../../sdk/`). Nothing of it goes into the calendar yet.

- `module.ts`: its routes (the Journal page's, `server/http.ts`), its made-up data for the testing data, and its lines of the privacy policy (`server/privacy.ts`).
- `viewer.tsx` and `viewer/`: the Journal page (below): its Days view (`JournalSection.tsx`), the side pane (`SidePane.tsx`), the player (`player.ts`) and its own small Markdown renderer (`markdown.ts`, the tree; `Markdown.tsx`, drawing it). `wire.ts`: what the page and the routes say to each other.
- `server/http.ts` and `server/journals.ts`: the page's routes, and the reads of the vault's `Journals/` they answer with, every path held inside it.
- `cli.ts`: `npm run journal`, which hands each run to a job's command: `grok-calls ...` to the Grok calls', anything else to the voice journals'. It stays at this path: the voice journals' launcher has it built in, and rituals' old `bin/ritual-voice-calls` hands its runs here.
- `jobs/voice-journal/`: the voice journals' job. `command.ts`, `npm run journal -- [run] [--dry-run] | status | retry <file> | install [--dry-run] | uninstall`: a pass, what a pass would do, the ledger, a failed recording tried again, and the launchd agent (`local.life-archive-voice-journal`, each day at 06:00) with the launcher Full Disk Access is given to, installed and removed. One pass (`round.ts`: which recordings have arrived and were not deleted in Voice Memos, the copy into the vault's `Journals/assets/`, the transcripts and the `journal-source-v1` record into `Journals/raw/`, the note to firstmate), what Voice Memos says of its recordings and when one has finished arriving (`recordings.ts`), the ledger (`ledger.ts`), and the launchd agent (`live.ts`). The transcribers themselves (OpenSuperWhisper and Nemotron) are the core's (`server/voiceTools.ts`), shared with any module that needs them, and reached through the SDK.
- `jobs/grok-calls/`: the Grok calls job (below).
- `src/day.ts`: the journal's day, from 06:00 to 06:00, which both jobs file by.
- `fixtures/`: a made-up voice journal for the tests and `npm run testing-data`: a vault with one recording (a made-up sound, a WAV a browser plays) transcribed into its `Journals/` by both engines, that day's clean journal and edit list, an older day written by hand, and the ledger with the recording done.

**Grok calls.** `npm run journal -- grok-calls` copies each finished call still in Grok Bot's cache (`~/Library/Application Support/Grok Bot/sand-client-persistence`, which the app keeps for a few days) into the vault's `Journals/raw/<journal day>/` as three files: the verbatim `voice-<id>.transcript.json` (the app's call record unchanged, the streamed partials joined into utterances), a readable `voice-<id>.transcript.md`, and the `voice-<id>.source.json` record of rituals' journal contract (`modules/rituals/HANDOFF.md`'s "Journal"). The files are its ledger: each is written once, synced to disk and never replaced, so a pass run twice, or two at once, only fills in what is missing; a saved transcript the cache would now render differently is kept and flagged `differs`. Calls are dated and filed in the archive's time zone (`timeZone` in its settings), which wins over `RITUAL_TIME_ZONE`, the zone rituals' job went by. It only reads the cache, refuses a journal home with no `raw/`, and prints one JSON line of counts and ids, never a word of a call. `npm run journal -- grok-calls install` (`--dry-run` prints it) writes its launchd agent, `local.life-archive-voice-calls`, which runs a pass when the cache changes (at most once a minute) and every 30 minutes, logging to `~/Library/Logs/LifeArchive/voice-calls.log`; `uninstall` removes it, and the journals stay. It was rituals' job until 8 November 2026 (`npm run rituals -- voice-calls install`): an agent rituals installed keeps its label and runs rituals' `bin/ritual-voice-calls`, which now hands the run here (rituals' README, "Voice calls"); `grok-calls install` writes it anew with this job's own program, after which nothing runs that wrapper.

**The Journal page** (docs/console.md's "Journal"; from 9 November 2026), second in the rail after Events, is A · Notebook's Days, the direction the captain chose ("lets go with A"), read-only: the days, a day drawn from its `Journals/<day>.md`, and beside it its outline, its sources (each recording playing and seeking, both transcripts) and the cleaner's edits; Obsidian edits a day ("Open in Obsidian", on the phone "Edit in Obsidian", `obsidian://open?vault=<the vault's folder name>&file=Journals%2F<day>`). Its routes, under `/life-archive/api/m/journal`, only read and only inside the vault's `Journals/` (`wire.ts` lists them):

| Route | Reads | Kept in the trail |
|---|---|---|
| `GET …/days` | the day files' names and sizes, and the names in each `raw/<day>/` | no (metadata) |
| `GET …/days/<day>` | `<day>.md`, and each `raw/<day>/*.source.json` | yes, `journal-day` |
| `GET …/days/<day>/raw/<file>` | a Markdown file of `raw/<day>/` (a transcript, an edit list) | yes, `journal-raw` |
| `GET …/days/<day>/assets/<path>` | a recording or picture of `assets/<day>/`, a byte range at a time (HTTP Range) so the player seeks | yes, `journal-asset`, its ranges folded into one row |

A day is named YYYY-MM-DD; every other step of a path is one name (never empty, never starting with a dot, never holding a slash); and a file is opened only once its real path, every link followed, is inside `Journals/` (whose own real path may be in iCloud Drive). Each read is kept in the trail of content reads as a viewer read before it is answered (`npm run archive -- content-log`), for the console's own page alone (and on the tailnet only the devices its ACL admits), never cached, and never handed to a model, by the captain's call ("logged reads on open, no model"). On a desk, opening the page opens its latest day; a phone reads nothing until a day is tapped. Editing in place on the desk, with a guard against a clash with Obsidian or iCloud, is the next step. To try the page, build the testing data (`npm run testing-data`): its made-up vault has a day with a recording (a made-up sound), both transcripts, its clean journal and edit list, and an older day written by hand.

**Its data** is the vault, the captain's own, which this module writes into in two places (`Journals/assets/<day>/voice-memos/` and `Journals/raw/<day>/`) and which the archive reads only through the Journal page; the voice journals' ledger, `modules/journal/ledger.json` in the archive's folder (which recordings are done, waiting or failed, by file name; its lock beside it), which a pass takes over once from where it was before the journal was a module (`voice-journal/ledger.json`); and the jobs' logs, `~/Library/Logs/LifeArchive/voice-journal.log` and `voice-calls.log`. The journals are content, the most private the archive keeps; the ledger and the logs are metadata (`server/privacy.ts`). The vault is backed up where it lives (iCloud Drive and Time Machine, for a vault kept there; docs/data.md's "Where the data lives"): the NAS backup leaves it out.

Switch the module off with `"modules": {"journal": false}` in the archive's `settings.json`: the core then loads nothing of it. Its launchd agents are installed only by their commands (`npm run journal -- install`, `npm run journal -- grok-calls install`), from the checkout whose archive keeps the journals, so a life archive without the module has no job and nothing to switch off; one with an agent installed keeps it running until its `uninstall`, whatever the switch says, since the agent is launchd's, not the server's.
